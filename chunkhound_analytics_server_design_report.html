ChunkHound Analytics Reporting — Design Proposal

Companion to ALGINF-5738 (client-side design) | Target: PDC — self-hosted MinIO (S3-compatible) | Generated: 2026-08-16 (rev. 4 — access control, read-only credential, retention) | Status: Pending Approval

Context

The ALGINF-5738 client-side design defines a store-and-forward analytics pipeline in ChunkHound: usage events buffered locally, then uploaded as unique JSONL objects directly to an S3-compatible bucket (self-hosted MinIO on PDC). There is no central ingestion server — the bucket is the receiving side. This design covers only the reporting/viewer layer: how to turn those many small JSONL objects into usable dashboards.

Recommendation: DuckDB (query engine, reading S3 directly via httpfs) + Metabase (dashboard/BI layer, via its community DuckDB driver). Both are free, self-hostable, and require no data movement — DuckDB queries the JSONL objects in place.

As of ALGINF-5738 rev. 3, each object contains one command_summary event per MCP tool call or CLI command — a single record per invocation with a nested providers breakdown (LLM/embedding/reranker calls and tokens by provider+model) rather than several flat event types. This affects query shape (see DuckDB Query Layer below) but not the architecture here — DuckDB + Metabase over S3 stays the same regardless of the exact event schema.

Design History

This is the third iteration of the server/reporting-side design — kept here rather than deleted, per the project's knowledge-preservation practice, since each prior decision was a real, reasoned step:

  1. superseded Rev. 1 — pluggable Elasticsearch/Loki ingestion server. Built for a case where the backend platform wasn't yet decided; dropped once a concrete backend was confirmed.
  2. superseded Rev. 2 — Prometheus + Grafana ingestion server. Confirmed backend (algo-infra-01), modeled on the bf_monitoring (bifrost) precedent: pull-based scrape, `prometheus_client` in-memory registry, `ServiceMonitor` CRD, Grafana dashboard-as-code. Fully designed, including a documented Scaling Limits analysis (confirmed sufficient for Phase 1 at ≤50 users).
  3. superseded Rev. 3 — direct-to-S3, reporting/viewer layer only. Superseded Rev. 2 once the decision was made to have clients write directly to an S3-compatible bucket instead of pushing to any server — this removes the ingestion server concept entirely. Established the DuckDB + Metabase architecture, but left access control, the reporting layer's own credential, and retention undefined.
  4. current Rev. 4 — implementation-readiness pass, this document. Closes the three gaps left open by rev. 3: who can access Metabase and how they authenticate (Access Control), a read-only credential for the reporting layer distinct from the client's write-only credential (Configuration & Deployment), and an explicit retention/lifecycle decision instead of an open non-goal (Retention & Lifecycle). No architectural changes from rev. 3 — same DuckDB + Metabase, direct-to-S3 design.

Key Design Decisions

  • No ingestion server decided — ChunkHound clients write directly to the bucket (per ALGINF-5738). Nothing to build or operate on a receiving side.
  • Query engine decided — DuckDB with the `httpfs` extension, configured against the MinIO endpoint, running `read_json_auto('s3://bucket/analytics/**/*.jsonl')` glob queries directly over the objects. Zero ETL; DuckDB is already core to ChunkHound itself, and its S3-compatible-endpoint support (custom `s3_endpoint`, `s3_url_style='path'`) is mature and explicitly tested against MinIO. researched Aug 2026
  • BI/dashboard layer decided — Metabase, via the actively-maintained community `metabase_duckdb_driver`, pointed at the DuckDB-over-S3 setup. Redash is the documented fallback (DuckDB is a first-class Redash source, slightly less full-featured dashboards/alerting) if Metabase's community driver ever becomes a blocker. researched Aug 2026
  • Deployment decided — Metabase self-hosted on PDC via Docker/Helm, matching established conventions. No custom application code to write at all for the reporting side — this is entirely off-the-shelf tooling configuration.

DuckDB Query Layer

DuckDB's `httpfs` extension is explicitly tested against AWS S3, MinIO, GCS, and lakeFS. Custom endpoints are first-class:

INSTALL httpfs; LOAD httpfs;
SET s3_endpoint='<minio-host>:<port>';
SET s3_url_style='path';
SET s3_use_ssl=false;      -- if MinIO is running without TLS internally
SET s3_access_key_id='...';
SET s3_secret_access_key='...';

SELECT * FROM read_json_auto('s3://<bucket>/analytics/**/*.jsonl');

Because the object key already encodes `repository`/`user`/date, queries can prune by path glob (e.g. `analytics/chunkhound/**/2026/08/**/*.jsonl`) as well as by the `repository`/`user`/`command` fields inside each JSON line — no separate index or catalog needed. DuckDB itself already ships inside ChunkHound, so this reuses in-house expertise rather than introducing a new query technology.

Querying the nested providers rollup: since ALGINF-5738 rev. 3 nests LLM/embedding/reranker activity as arrays-of-objects per event (providers.llm[], providers.embedding[], providers.reranker[]), per-provider/model breakdowns need UNNEST:

SELECT repository, command,
       p.provider, p.model, SUM(p.calls) AS calls,
       SUM(p.input_tokens) AS input_tokens, SUM(p.output_tokens) AS output_tokens
FROM read_json_auto('s3://<bucket>/analytics/**/*.jsonl'),
     UNNEST(providers.llm) AS p
GROUP BY repository, command, p.provider, p.model;

Command-level rollups (e.g. calls per command per repository) don't need UNNEST at all — they read directly off the top-level fields.

Access Control new in rev. 4

Rev. 3 left "who can see the dashboards, and how do they log in" undefined. The original intent was to follow the same precedent as the dropped Rev. 2 (Grafana on algo-infra-01, modeled on bf_monitoring): PDC-hosted internal tools authenticate via the existing PDC SSO/OIDC identity provider rather than standing up local accounts. That runs into a real licensing gap, below, so Phase 1 falls back to local accounts instead.

SSO licensing gap researched Aug 2026

Metabase's SAML and JWT SSO integrations — the mechanisms that would federate against PDC's SSO/OIDC identity provider — are Metabase Pro/Enterprise features, not available in the free open-source edition this design otherwise relies on for everything else (see Viewer Evaluation above). Open-source Metabase's only built-in SSO options are Google Sign-In (OAuth) and LDAP bind. Neither is confirmed available against PDC's identity provider yet, and an Enterprise license is a separate procurement/budget decision outside this design's scope — so SSO is deferred rather than blocking the rest of the rollout on it.

Phase 1 — local accounts, no SSO decided

  • Authentication decided — Metabase's built-in local account system (email + password), no SSO. Exactly two accounts are provisioned: one admin account (deploys/maintains the instance, configures the DuckDB connection, full edit rights) and one shared viewer account (view-only), handed to whoever needs to see the dashboards — engineering leads and the requester, Nir S., for now.
  • Why a shared viewer account instead of per-person accounts decided — with only local auth and no SSO, provisioning/deprovisioning individual Metabase accounts by hand doesn't scale and isn't worth automating for Phase 1's small audience; a single shared viewer login is simplest and matches the "one shared credential" pattern already used elsewhere in this design (the client's write credential, Metabase's own read-only S3 credential).
  • Authorization decided — the admin account has full edit/admin rights; the viewer account has view-only permission on a single Collection containing the analytics dashboards, with no query/SQL access and no visibility into the underlying DuckDB connection settings or credentials.

Future — SSO once unblocked deferred

Once PDC confirms LDAP bind availability, Google Workspace-backed accounts, or an Enterprise license is approved, the original intent — SSO against PDC's identity provider, per-person accounts, a real read-only viewer group — should replace the Phase 1 shared-account approach above. Tracked as a follow-up, not solved by this revision.

Why not per-repository/per-team scoping non-goal — independent of the SSO question, Phase 1 has one shared viewer scope for all analytics dashboards, matching the client-side design's Phase 1 decision to use one shared write credential rather than per-team scoping. Finer-grained scoping (e.g. a team only seeing its own repositories' data) is deferred until there's real demand for it.

Reliability

  • There is no ingestion path to fail — clients write directly to the bucket and retry on failure per the client-side design; the reporting layer is purely read-only against whatever objects already exist.
  • DuckDB re-scans the bucket per query (or per Metabase-scheduled refresh) — there's no persistent index to go stale or need rebuilding. A slow/unavailable MinIO endpoint simply makes the next dashboard refresh slow or fail; it doesn't corrupt or lose any client-side data.
  • As object count grows, glob-scan cost grows with it — the object-key partitioning by repository/user/date (from the client-side design) lets queries narrow the scan via path prefixes instead of listing the entire bucket, keeping this manageable well beyond Phase 1 volumes.

Configuration & Deployment

Entirely off-the-shelf: a Metabase container (official image + the `metabase_duckdb_driver` JAR in its `plugins/` directory) deployed via Helm to a PDC namespace, with an `init.sql` loading `httpfs` and setting the MinIO endpoint/credentials at driver startup. No custom application code, no new repository needed for this side of the design (contrast with the dropped Rev. 2, which required a bespoke FastAPI service, Helm chart, and `ServiceMonitor`).

Read-only credential scheme new in rev. 4

The client-side design (ALGINF-5738) uses one shared, write-only credential distributed to every ChunkHound install via environment variable. That credential must not be reused here — a write-only credential typically can't read, and even if it could, reusing a broadly-distributed developer-facing credential for the reporting layer would mean every developer's machine effectively also holds read access to every other user's analytics data.

Because MinIO issues independent access keys per policy, this is a new key with a read-only bucket policy, generated separately from the client-side write-only key — not a scoped-down copy of it.

Retention & Lifecycle new in rev. 4

Rev. 3 left this as an open non-goal. Given the object key already partitions by repository/user/date (from the client-side design), a bucket-native lifecycle rule is sufficient — no application code or DuckDB/Metabase change needed.

  • Decision decided — a MinIO bucket lifecycle rule expires objects under the analytics/ prefix after 180 days. Chosen as a starting point that comfortably covers quarter-over-quarter usage trend analysis without keeping per-user activity indefinitely; this is a bucket-admin config value, not code, and can be revisited without a design change.
  • Why not shorter — Metabase dashboards are expected to answer questions like "usage trend this quarter vs last," which needs at least ~2 quarters of history online at once.
  • Why not longer / indefinite — per-user activity data has a real privacy cost to retaining (see the privacy_mode discussion in ALGINF-5738); an explicit expiry bounds that exposure instead of accumulating it forever by default.
  • Ownership — configuring the lifecycle rule is a one-time MinIO administration task on the same bucket used by the client-side design, done alongside the rest of the deployment in Configuration & Deployment; it is not something ChunkHound or Metabase enforce in code.

Non-Goals

  • out of scope No custom ingestion service of any kind — superseded entirely by direct-to-S3 client writes.
  • out of scope No dollar-cost computation — consistent with ALGINF-5738; token/request counts are queryable as-is, cost conversion is a downstream SQL/dashboard calculation if ever needed.
  • out of scope No data warehouse / ETL pipeline — DuckDB queries the raw JSONL objects in place; no transformation or loading step.
  • out of scope No per-repository/per-team scoping of Metabase view access in Phase 1 — see Access Control.
  • superseded (rev. 4) No long-term retention policy defined here — resolved; see Retention & Lifecycle.

Verification

  1. Stand up a local MinIO (docker-compose), upload a handful of sample JSONL objects matching the ALGINF-5738 key scheme, and confirm a local DuckDB instance can `read_json_auto` them via `httpfs` with the expected schema.
  2. Deploy Metabase with the community DuckDB driver locally, point it at the same MinIO instance, and confirm a basic query (e.g. `command_summary` counts by `repository`/`command`, and an `UNNEST`-based per-provider/model token breakdown) renders correctly.
  3. Deploy to PDC against the real MinIO bucket once ChunkHound clients are uploading real data; confirm dashboards reflect live usage.
