TurboVec POC — Summary & Results

ChunkHound | test-crates/turbovec-poc | Corpus: qwen3-embedding-4b, this repo's own indexed code

Overview

The design doc turbovec_integration_design_report.html proposed replacing ChunkHound's DuckDB-VSS/HNSW vector search with the turbovec Rust crate — claiming 16x compression at 4-bit, ~0.997 recall@1, and zero-re-embedding restarts. Rather than commit 2–3 weeks to that migration on faith, we built a standalone, throwaway benchmark against this repo's own real, indexed code embeddings and measured every headline claim directly.

The recall@1 shortfall looked alarming at first, so we ran two follow-up diagnostics (below) — the short version: it's mostly a near-duplicate-chunk ranking-ambiguity effect that would challenge any approximate method, with the 256-dim embedding truncation contributing a real but smaller share. Full detail in Recall@1 Gap Diagnosis.

What We Built

Everything lives in test-crates/turbovec-poc/ — a fully standalone Rust crate, decoupled from ChunkHound's production build (no schema, PyO3, or `chunkhound_native` changes). Three layers:

  1. Offline benchmark (bench) — loads this repo's real 256-dim embeddings (73,474 vectors, held-out query split), measures compression, recall@k, latency, and the index serialize/reload roundtrip at both 2-bit and 4-bit quantization.
  2. Live demo (serve + demo_compare.py) — an interactive REPL: type a query, it's embedded once, and both the existing DuckDB-VSS path and the new TurboVec index answer side by side.
  3. Dimension-comparison matrix (probe_dim + probe_native_dim.py) — re-embeds a matched 4,000-corpus/300-query sample at multiple dimensionalities to isolate exactly how much of the recall gap is caused by dimension vs. quantization noise.

All three reuse the same shared measurement code (src/lib.rs: fixture loading, cosine ground truth, recall/compression math) so numbers are comparable across every run.

Recall@1 Gap Diagnosis

Why does recall@1 (0.89 at production scale) fall so far short of the design doc's claimed 0.997? Two mechanisms were tested, cheapest first.

Stage A — near-tie correlation (free, no new API calls)

For every held-out query, we captured the exact top1–top2 cosine score gap and checked whether it correlates with TurboVec getting the top-1 answer right:

bit_widthMean gap on hitsMean gap on missesRatio
2-bit0.0637 (n=405)0.0044 (n=95)~14x
4-bit0.0589 (n=445)0.0009 (n=55)~65x
Misses cluster overwhelmingly on queries where the true top-1 and top-2 chunks were already almost indistinguishable in exact, unquantized cosine similarity (mean gap 0.0009 — essentially a coin flip). This corpus has many near-duplicate chunks (near-identical test files, repeated patterns); when two candidates are that close, quantization noise flipping the winner isn't really a TurboVec defect — any approximate method would struggle the same way.

Stage B — native vs. truncated dimension, matched subset

Isolates dimensionality specifically: same 4,000/300 sample, same texts, embedded at 256-dim (truncated) vs. native 2560-dim, everything else held constant.

DimensionRecall@1 (4-bit)Δ vs. 256-dim
256 (truncated)0.9367—
1536 (derived)0.9600+2.3 pts
2560 (native)0.9700+3.3 pts

Truncation is a real, measurable contributor — recall@1 improves monotonically with dimension on identical data. But it's not the whole story: even at full native dimension, recall@1 (0.97) is still below the design doc's 0.997 claim.

Bottom line: the 0.89-vs-0.997 gap is mostly a near-tie / corpus-scale effect (Stage A) that would challenge any approximate method, with the 256-dim truncation contributing a real but smaller share (Stage B, ~3 points). Neither points to a fundamental TurboVec defect; both suggest the design doc's 0.997 figure was measured under different conditions than ChunkHound's real, near-duplicate-heavy code corpus.

Design Doc Corrections

Found by reading the real turbovec 0.9.0 source directly, not just its docs:

  1. No IdMapIndex::from_parts() or in-memory to_bytes()/from_bytes(). The only reconstruction path is file-based write()/load() — proven bit-identical by our roundtrip test.
  2. TurboQuantIndex::from_parts() and its supporting accessors were all pub(crate) in the published crate — not reachable from any downstream crate, which invalidated the design doc's "reconstruct from per-vector rows without a whole snapshot" fallback path as written. Resolved — see below.
  3. turbovec unconditionally requires a system BLAS library on Linux, contradicting the "no new system libraries" claim. This environment needed sudo apt-get install libopenblas-dev before it would even build. Resolved — Linux-only, and a build-time-only cost; see BLAS Dependency & Distribution.
  4. 4-bit compression is ~7.3–7.9x in practice, not 16x — the design doc's 16x figure is actually the 2-bit number, and real per-vector id+scale overhead pulls the achievable ratio down further.

BLAS Dependency & Distribution

Traced the root cause down to turbovec's own build.rs, which picks a BLAS backend per target OS:

OSWhat build.rs linksExtra install needed?
Linuxcargo:rustc-link-lib=openblasYes — libopenblas, the only platform where this is a real constraint
macOScargo:rustc-link-lib=framework=AccelerateNo — ships with every macOS install
Windowsfalls through to _ => {} → ndarray's pure-Rust matrixmultiplyNo — nothing to link at all
Windows and macOS need zero extra install, build or runtime — this is a Linux-only problem, by design of turbovec's own build script.

Distribution plan — never reaches the end user

The apt-get must stay a CI/build-time concern, never something pip install chunkhound requires. This repo already solves an equivalent problem for DuckDB (Cargo.toml's DUCKDB_DOWNLOAD_LIB/DUCKDB_STATIC — resolved once in CI, invisible in the shipped wheel), and BLAS should follow the same pattern.

Gap found: .github/workflows/release.yml's build-native-wheel job builds the Linux wheel on plain ubuntu-latest via maturin build --release — no manylinux container, no auditwheel repair. A naive dynamic link against libopenblas today would ship a wheel that only works on hosts that already happen to have it installed.

Options, best first:

  1. Static-link OpenBLAS in CI — openblas-src's static feature plus gfortran/cmake on the runner (no proxy issue on GitHub-hosted runners, unlike this local machine). Self-contained .so, zero runtime dependency — same approach numpy/scipy wheels use.
  2. Dynamic link + auditwheel repair — vendor libopenblas.so.0 into the wheel and patch RPATH; needs switching this job to a manylinux-compliant build, which it doesn't do today.
  3. Prebuilt BLAS from PyPI (e.g. scipy-openblas64) — avoids any system package manager call in CI entirely.
Bottom line: solvable without touching the end user's machine on any OS, and macOS/Windows need no build changes at all.

from_parts() Problem — Resolved

The design doc's embeddings_quantized table has one stated purpose: rebuild the search index directly from durable per-vector packed bytes if the main snapshot is ever lost or corrupted, with no re-embedding. That required from_parts(), which wasn't public. Two options were built and tested against this repo's real corpus — both work.

Option 1 — pin to the unreleased upstream fix

The exact fix (PR #204, making from_parts() public) is merged on turbovec's main branch but not yet released to crates.io. We git-pinned Cargo.toml to that exact commit (ae31ba3).

Passes. A new test extracts packed_codes()/scales()/tqplus_shift()/tqplus_scale() from a live index, calls the now-public from_parts(), and gets bit-identical search results — no snapshot blob, no re-embedding. Existing tests and benchmark numbers confirmed unchanged (regression check).

Real gap found: IdMapIndex still has no accessor for its inner index, so this only works by going around IdMapIndex and hand-rolling the id-reattachment layer ourselves. from_parts() being public unblocks the primitive, not the full ready-made object the design doc's schema implies. Caveat: it's an unreleased, untagged commit — safe by content-addressed SHA pinning, but not a versioned release.

Option 3(C) — durability engineering, no from_parts() needed

Works against the stable, published crate today: CRC32-checksummed, rotating snapshots on top of the one mechanism turbovec's public 0.9.0 API already gives for free (write()/load()), plus keeping ChunkHound's existing float32 table as the true last resort.

TestResult
Corrupt one snapshot generationFalls through to the next generation cleanly, identical search results
Corrupt every generationReports failure cleanly — no panic, no silent garbage index
Total snapshot loss → rebuild from stored float32Identical search results; 0.45s (2-bit) / 0.62s (4-bit) real cold-start cost on the full 72,974-vector corpus
Storage cost (float32 + N=2 rotation)+27.3% vs. today's float32-only baseline (≈95.2 MB vs. ≈74.7 MB)
Sub-second local rebuild, no network calls — confirms "no re-embedding needed" is achievable today, at a modest, now-measured disk cost.

Recommendation: ship Option 3(C) as the safety net regardless — it's cheap, uses only the stable published API, and is now proven, not just designed. Treat Option 1 as the upgrade path once turbovec actually cuts a release incorporating the fix.

Go/No-Go Recommendation

  • Recall@10 = 1.0000 at every dimension and both bit-widths tested — the metric that matches ChunkHound's actual default (page_size=10) passes comfortably everywhere.
  • Recall@1 is diagnosed, not just measured: mostly an inherent near-duplicate-corpus effect, partly a truncation cost. Only matters if a caller depends on a single top-1 answer rather than the full top-k.
  • Compression (7.3–15.6x depending on bit-width/dimension) is a large, real win over float32, just not the headline "16x."
  • Search speed beats brute-force cosine at every dimension tested, with the gap widening at production scale.
  • Engineering risks found and resolved: the system BLAS dependency is Linux-only (macOS/Windows need nothing extra) and solvable entirely at CI build time — see BLAS Dependency & Distribution. The missing from_parts() public API — the bigger risk — now has two tested, working solutions (above); neither requires forking or patching turbovec.

Net: TurboVec looks viable for ChunkHound's actual usage pattern (top-10 retrieval), with design-doc corrections folded into a proven path forward, and one open question (top-1-specific reliance) to confirm isn't load-bearing anywhere in the product.
