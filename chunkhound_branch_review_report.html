Database Compaction

DuckDB accumulates fragmentation over time as ChunkHound continuously indexes and deletes file chunks during codebase analysis. Free blocks from deleted rows, re-indexed chunks, WAL segments, and stale HNSW index metadata accumulate — degrading query performance and wasting disk space. The compaction system reclaims this space via a full EXPORT/IMPORT/SWAP cycle that rebuilds the database from scratch without any search downtime.

Two modes: Blocking — used by the CLI repack command, pauses all operations until complete. Background — used by the MCP server daemon, non-blocking with a post-compaction callback to trigger reindexing.

Architecture

Compaction Cycle (7 Steps)

  1. optimize_tables() — Run CHECKPOINT and per-table ANALYZE before the full cycle to reclaim WAL space and update statistics first.
  2. Acquire lock · Capture HNSW snapshot · soft_disconnect() — Serialize access via threading.Lock, snapshot HNSW index definitions for post-import recreation, then close the live connection.
  3. EXPORT DATABASE → Parquet staging dir — Export all tables to a temporary directory in Parquet format. The staging dir is created adjacent to the live database file.
  4. Create new DB · IMPORT DATABASE — Open a fresh DuckDB file and IMPORT from the Parquet staging dir. The result is a fully compact database by construction.
  5. Recreate HNSW indexes — Replay the HNSW snapshot in the new database. VSS vector data survives because it is stored as regular table rows, not index metadata.
  6. Write PHASE_PRE_SWAP intent · Atomic RENAME — Write a crash-recovery sentinel file, then atomically rename the compact DB into the production path (rename old → .old, rename compact → live). This is the point of no return.
  7. Probe integrity · Cleanup · Replay deferred events — Verify the swapped DB is readable via _probe_db_valid(), delete old files and staging dir, then drain and replay any filesystem events that were deferred during compaction.

Event Deferral Mechanism

During compaction the database connection is closed. The RealtimeIndexingService maintains four defer sets to safely capture and replay filesystem events that arrive during this window:

AttributePurpose
_compaction_deferred_filesFile modification/creation events received while compaction is active
_compaction_deferred_removalsFile deletion events received while compaction is active
_compaction_deferred_directoriesDirectory scan events received while compaction is active
_drained_compaction_removalsRemovals drained from the live queue before compaction begins — prevents double-processing on replay
Crash Recovery: If the process crashes after the intent file is written but before RENAME completes (PHASE_PRE_SWAP), the next startup detects the sentinel and completes the swap atomically. The database is never left in a partially-swapped state.

Embedding Migration — Matryoshka Protocol

This feature enables migrating an existing ChunkHound database from full-dimension embeddings to a smaller target dimension without re-embedding via the network. For models that support the matryoshka principle — where the first n dimensions of a large embedding carry equivalent semantic information to a native n-dimension model — truncation can be performed locally with L2 normalization, saving API cost and latency entirely.

Architecture

Matryoshka Protocol Properties

PropertyDescription
native_dimsThe model's native embedding dimension (e.g. 3072 for OpenAI text-embedding-3-large)
client_side_truncationWhen True, truncation is performed locally — no API call with a reduced dimension parameter
output_dimensionsTarget storage dimension (e.g. 1536, 768, 512)
L2 normalizationApplied after truncation to preserve unit-norm invariant required by cosine-similarity HNSW search

Key Behaviors

  • Migration is wired into generate_missing_embeddings() — dimension mismatch is detected automatically and triggers _migrate_from_full_embeddings()
  • Supported providers: OpenAI (text-embedding-3-* series), VoyageAI
  • No API calls for matryoshka models — pure NumPy slice + L2-normalize
  • Compaction is suppressed during migration to prevent contention during bulk DB writes

Git Diff Semantic Search

DiffAwareSearchService is a decorator around the existing search service that enables semantic search within git history — specifically within the changed regions of recent commits. This lets an AI assistant answer "find where we changed the embedding batch logic in the last 5 commits" without manually reading diffs.

Architecture — Decorator Pattern

User Flow

# Search changed regions in last 5 commits
chunkhound search "embedding batch logic" --last-n 5

# Search within a specific commit range
chunkhound search "compaction threshold" --commit-range main..HEAD

# Search a single commit's changes
chunkhound search "HNSW index recreation" --commit-hash abc1234

# Search both DB and git diff results together
chunkhound search "optimize()" --last-n 3 --source both
  1. Parse git log — Runs git log --patch for the specified range or commit count
  2. Extract changed regions — Parses the unified diff to isolate added/modified code chunks per file
  3. Embed diff chunks — Uses the configured embedding provider to vectorize changed regions in batches
  4. Semantic search — Vector similarity search against the embedded diff chunks
  5. Merge results — Depending on --source mode, merges diff results with DB results and deduplicates

LLM Provider Registry Refactor

The LLM provider system was refactored from a subclass-per-provider hierarchy to a data-driven registry. Adding a new provider no longer requires a new Python class — it's an entry in a registry dict.

Before

  • One subclass per provider: GrokLLMProvider, DeepSeekLLMProvider, etc.
  • Provider capabilities hardcoded in each class
  • Manual wiring in factory methods
  • grok_llm_provider.py (deprecated, now removed)

After

  • Single provider_registry.py with data-driven factory
  • claude_model_resolution.py (260 lines) for dynamic selection
  • llm_config.py expanded to 1154 lines with full registry
  • New: Claude Opus 4.8, Gemini thinking budget, reasoning effort control
