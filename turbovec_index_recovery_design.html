Design: TurboVec Index Recovery (Two Options)

docs/superpowers/specs/2026-08-04-turbovec-index-recovery-design.md | Status: Approved, pre-implementation

Context

The TurboVec integration design doc (turbovec_integration_design_report.html) proposed replacing DuckDB-VSS/HNSW with the turbovec Rust crate, including an embeddings_quantized table whose sole stated purpose is: "if the turbovec_indexes snapshot is stale or corrupt, rebuild the search index directly from packed codes without any embedding API calls."

A POC (test-crates/turbovec-poc/) validated this and every other headline claim against this repo's own real, indexed embeddings, and found the mechanism above unbuildable against the published turbovec 0.9.0 crate: TurboQuantIndex::from_parts() and its accessors (packed_codes(), scales(), tqplus_shift(), tqplus_scale()) are pub(crate), not reachable from any downstream crate. The exact fix is merged upstream on turbovec's main branch (commit ae31ba3, PR #204) but not yet released to crates.io.

Two recovery designs were built and tested in the POC, both passing against this repo's real corpus:

  • Option A POC "3(C)" — checksummed, rotating whole-index snapshots (the one mechanism the published 0.9.0 API gives for free) plus ChunkHound's existing float32 table as the true last resort — no from_parts() needed at all.
  • Option B POC "Option 1" — git-pinned to the unreleased upstream commit, proving the design doc's original per-vector from_parts() mechanism works end to end.

This document is the production design for both, scoped specifically to index recovery — not the full DuckDB-VSS→TurboVec migration.

Scope

In scope: the Rust-side persistence and recovery lifecycle for a TurboVec-backed vector index — the same open/write_batch/needs_compaction/run_compaction lifecycle DuckDbHnswBackend (src/db/duckdb_backend.rs) already implements via the DbBackend trait (src/db/mod.rs).

Out of scope: exposing TurboVec search via PyO3 (design doc's "Phase 3"); dropping the float32 embeddings_{dims} tables (design doc's "Phase 4" — a separate, later decision per Rollout); any change to embedding generation, chunking, or the existing DuckDB-VSS/HNSW code path itself.

Coexistence model: sequential, not dual-path. Option A is the real, shipped implementation. Option B is designed in full detail now so that swapping it in later (once turbovec cuts an actual tagged release) is a scoped, understood migration — not a rediscovery effort. No runtime/compile-time switching logic between A and B is built; the switch happens by changing the turbovec dependency and updating one backend module.

Rollout model: opt-in via a new database.vector_backend config flag (default "duckdb_hnsw"). Existing installs are unaffected until someone opts in.

Shared Foundation

Integration point: create_backend(cfg: DbConfig) -> Box<dyn DbBackend> (src/db/mod.rs) currently hardcodes DuckDbHnswBackend::new(cfg). Add:

pub enum VectorBackend {
    DuckDbHnsw, // default
    TurboVec,
}

as a new field on DbConfig, and branch in create_backend accordingly. DbBackend's trait signature (open, close, write_batch, needs_compaction, run_compaction, plus the default-no-op drop_all_hnsw_indexes/ensure_all_hnsw_indexes) needs no changes — this is exactly the abstraction point the trait already exists for.

New module: src/db/turbovec_backend.rs, implementing DbBackend, alongside duckdb_backend.rs. Shares the same DuckDB Connection and existing chunks/files tables; only the vector-storage tables differ from DuckDbHnswBackend.

New table (both options): turbovec_indexes — the warm-snapshot cache.

CREATE TABLE turbovec_indexes (
    provider    TEXT NOT NULL,
    model       TEXT NOT NULL,
    dims        INTEGER NOT NULL,
    bit_width   INTEGER NOT NULL,
    generation  INTEGER NOT NULL,  -- cycles 0/1
    payload     BLOB NOT NULL,
    checksum    BIGINT NOT NULL,   -- CRC32
    n_vectors   INTEGER NOT NULL,
    updated_at  TIMESTAMP NOT NULL,
    UNIQUE (provider, model, dims, generation)
);

The checksummed-rotation logic (write two generations, verify-on-load, fall through) ports directly from the POC's src/snapshot.rs (write_checksummed, load_verified, load_any_verified) — it doesn't depend on which option is active.

New Cargo.toml dependencies: turbovec (version per option, see below), crc32fast, blas-src/openblas-src (features = ["openblas"] / ["cblas", "system"]) — plus, critically, an extern crate blas_src as _; shim in whatever binary/lib target links turbovec, or the linker drops it as "unused" (a real gotcha the POC hit).

Build/ops impact (new, not optional): turbovec unconditionally requires a system BLAS library on Linux via ndarray's blas feature. This machine needed sudo apt-get install libopenblas-dev before cargo build would even link. AGENTS.md and RELEASING.md need a new documented build prerequisite, and release-wheel-building CI images must include it before vector_backend=turbovec can be enabled anywhere — see Rollout.

Option A — Ships Now turbovec 0.9.0, published

Write path

Inside write_batch, additive to the existing logic:

  1. Embeddings arrive as Vec<f32> per chunk — unchanged.
  2. L2-normalize (so TurboVec's raw score is cosine-comparable, per POC finding).
  3. IdMapIndex::add_with_ids(&vectors, &chunk_ids) on an in-memory index held per (provider, model, dims) in a HashMap for the process lifetime.
  4. At batch-end (not per-vector — write-amplification mitigation): snapshot::write_checksummed(&index, path) targeting the next rotation generation, UPSERT into turbovec_indexes.
  5. insert_embeddings_txn (the existing float32 write path) is completely unchanged. embeddings_{dims} keeps being written exactly as today — this is what makes Option A additive rather than a rewrite.

Read/recovery path

On open():

  1. Try generation 0, then generation 1 (checksum-verified via load_any_verified) — first match wins.
  2. If both missing/corrupt: SELECT chunk_id, embedding FROM embeddings_{dims} WHERE provider=... AND model=..., batch into add_with_ids. Measured cold-start cost (POC, real data): 0.45s at 2-bit / 0.62s at 4-bit for 72,974 vectors — scales roughly linearly; log a warning if it exceeds a configurable threshold on much larger corpora.

Error handling

  • Snapshot write I/O failure → new DbError::SnapshotWrite(io::Error) variant, propagated like existing compaction errors.
  • Both generations corrupt and the float32 rebuild fails (e.g. embeddings_{dims} itself missing/corrupt) → the true catastrophic path. Surface a clear, actionable error ("semantic search unavailable for this partition, re-run indexing") — never silently return an empty or wrong index.

Migration

Purely additive: CREATE TABLE IF NOT EXISTS turbovec_indexes, then a one-time cold-start rebuild from existing float32 data on first open() after a user flips the config flag. No destructive step; fully reversible (flip the flag back — embeddings_{dims} was never touched).

Storage cost (measured, POC)

Float32 baseline (72,974 × 256-dim) ≈74.7 MB. N=2 checksummed rotation at 4-bit ≈20.4 MB (2 × the measured 140 B/vector single-snapshot cost). Total with both live: ≈95.2 MB, +27.3% vs. today's float32-only baseline.

Option B — Future Release once turbovec ships past ae31ba3

New tables

embeddings_quantized — the per-vector durable store the original design doc wanted:

CREATE TABLE embeddings_quantized (
    chunk_id     INTEGER NOT NULL,
    provider     TEXT NOT NULL,
    model        TEXT NOT NULL,
    dims         INTEGER NOT NULL,
    bit_width    INTEGER NOT NULL,
    packed_codes BLOB NOT NULL,
    scale        REAL NOT NULL,
    created_at   TIMESTAMP NOT NULL,
    UNIQUE (chunk_id, provider, model)
);
Schema nuance found by the POC, not in the original design doc: tqplus_shift/tqplus_scale are calibrated once per partition, per-coordinate (length = dims), not per vector — they don't belong in embeddings_quantized. A second, tiny table is needed instead.
CREATE TABLE turbovec_calibration (
    provider      TEXT NOT NULL,
    model         TEXT NOT NULL,
    dims          INTEGER NOT NULL,
    bit_width     INTEGER NOT NULL,
    tqplus_shift  BLOB NOT NULL,
    tqplus_scale  BLOB NOT NULL,
    updated_at    TIMESTAMP NOT NULL,
    UNIQUE (provider, model, dims, bit_width)
);

Missing this would mean every rebuild silently used wrong/default calibration.

The id-reattachment gap

Even in the tested unreleased commit, IdMapIndex has no accessor for its inner TurboQuantIndex. Option B's backend cannot call an IdMapIndex::from_parts() — it doesn't exist. It must build a bare TurboQuantIndex via the now-public from_parts() and wrap it in a new, hand-rolled type:

struct RecoveredIndex {
    inner: TurboQuantIndex,
    slot_to_id: Vec<u64>,
    id_to_slot: HashMap<u64, usize>,
}

This re-implements the handful of lines IdMapIndex uses internally for exactly this purpose, since that version is private to the turbovec crate.

Write path

Same as Option A through add_with_ids. Additionally, at batch-end: extract packed_codes()/scales() (per-vector, sliceable by slot) and tqplus_shift()/tqplus_scale() (per-partition), UPSERT the per-vector slices into embeddings_quantized keyed by chunk_id, UPSERT the calibration arrays into turbovec_calibration. turbovec_indexes (the warm-snapshot cache) is unchanged from Option A — still the fast path; embeddings_quantized is the fallback, not a replacement for it.

Read/recovery path

Try turbovec_indexes generations first (identical to Option A). If both are gone: SELECT packed_codes, scale FROM embeddings_quantized WHERE ... ORDER BY <insertion order>, SELECT tqplus_shift, tqplus_scale FROM turbovec_calibration WHERE ..., concatenate into the flat arrays from_parts() expects, call it, wrap in RecoveredIndex. No re-quantization CPU cost — the design doc's original "rebuild from packed bytes" promise, now real and tested (POC's from_parts_reconstructs_index_identical_to_original, bit-identical search results).

Error handling

from_parts() returns Result<_, FromPartsError> (~15 variants) — map into DbError; mostly "shouldn't happen unless the DB itself is corrupt," since we control what gets written. A partial embeddings_quantized read (some chunk_ids missing/decode-fail, most present) must abort the whole-partition rebuild, not silently return an index missing some vectors — a silently-incomplete index is a worse correctness bug than a loud failure.

A→B migration (once a release ships)

  1. Backfill embeddings_quantized+turbovec_calibration from the already-built in-memory indexes (cheap, no re-embedding — same add_with_ids-then-extract logic as the write path, run once over existing data).
  2. Run with both float32 and embeddings_quantized live for a confidence-building period.
  3. Drop embeddings_{dims} in a separately-decided, later phase (design doc's original "Phase 4") — not bundled into "upgrade to the new turbovec release."

Testing Strategy

Port the POC's already-passing tests directly:

  • Rust: a corruption-recovery test (build small index → write 2 checksummed generations → corrupt gen 0 → assert fallthrough to gen 1, identical search → corrupt both → assert clean error) and a rebuild-from-floats test (simulate missing snapshot → rebuild via add_with_ids → assert identical results) — near-verbatim ports of the POC's corruption_recovery.rs/rebuild_from_floats.rs.
  • Python, mirroring the existing tests/test_rust_db_writer.py pattern (pytest.importorskip("chunkhound_native", ...), fresh DuckDB connection post-close): open RustDbWriter with vector_backend="turbovec", write a batch, close, reopen, verify turbovec_indexes is populated and recovery behaves correctly through the actual PyO3 boundary.
  • Parity test: adapt the POC's demo_compare.py side-by-side logic into an automated check — assert overlap@10 between TurboVec-backed and DuckDB-VSS results stays above a threshold (e.g. ≥0.95) on a small real fixture corpus.
  • Option B's tests (ported from_parts_reconstructs_index_identical_to_original, plus new ones for the embeddings_quantized+calibration read path) are written against a git-pinned dependency on a feature branch, same as the POC — they cannot run in CI on main until a real release ships and Cargo.toml updates for real.

Rollout

  1. Merge Option A behind database.vector_backend (default off) — zero behavior change for anyone who doesn't opt in.
  2. Internal dogfood (this repo's own config, or a few volunteer users) to validate recall/latency/compression against real day-to-day usage, beyond the POC's held-out benchmark.
  3. Once a soak period builds confidence, consider flipping the default — the flag stays as an escape hatch regardless.
  4. (Separate, later decision, not part of this design) — eventually consider retiring the DuckDB-VSS/HNSW path entirely; Option B's own float32-drop is a similarly separate, later call.
Observability: log at INFO whenever recovery falls back past generation 0 ("generation 0 failed checksum, using generation 1"; "both snapshots missing, rebuilt from float32 in 0.6s") — recovery should never be silent.
Build prerequisite: libopenblas-dev (Linux) / platform equivalent must be added to CI wheel-building images before step 1 ships to anyone, including internal dogfooding.

Non-Goals

  • Exposing TurboVec search via PyO3 (a separate design, this repo's "Phase 3").
  • Dropping embeddings_{dims} float32 tables (a separate, later decision for both options).
  • Any dual-path runtime switching between Option A and Option B — the coexistence model is sequential.
  • Retiring DuckDB-VSS/HNSW — out of scope until TurboVec has proven itself in production under the opt-in flag.
