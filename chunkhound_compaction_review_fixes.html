Issue 1 — _last_error Missing Lock Protection Critical

File: chunkhound/services/compaction_service.py  ·  lines 86, 90, 248, 258, 265

Problem

_last_error is written from async context without holding self._lock (a threading.Lock). The last_error property and clear_last_error() also read/write without the lock. This creates a narrow race where the MCP server briefly reports a clean status between two writes — or reads a partially-cleared value while a new error is being stored.

Race scenario: Background compaction stores _last_error = cb_err (line 258) → concurrent MCP RPC reads last_error (line 86) → compaction finally block clears to None (line 248). The read sees stale or half-cleared state with no lock to prevent it.

Fix — 5 sites, same pattern

last_error property (line 86)
@property
def last_error(self) -> Exception | None:
    with self._lock:
        return self._last_error
clear_last_error() (line 90)
def clear_last_error(self) -> None:
    with self._lock:
        self._last_error = None
_do_compaction_with_callback — lines 248, 258, 265 (same pattern for all 3)
# Each bare assignment becomes:
with self._lock:
    self._last_error = None   # or cb_err or e
threading.Lock is safe to acquire from async code for these fast writes — no async boundary is crossed and no other lock is held at these points, so there is no deadlock risk.

Issue 3 — _post_compaction_reindex Loses Deferred Work on Restore Failure Important

File: chunkhound/mcp_server/base.py  ·  lines 1370–1424

Problem

Inside the except Exception as e: block, three restore_* calls execute before _mark_background_compaction_failure. If any restore call raises (e.g., database temporarily unavailable), the failure marker is never set. pending_recovery stays False, _attempt_post_compaction_recovery sees no retry needed, and all deferred work is silently lost.

Data-loss scenario: Compaction succeeds → reindex fails → except block enters → restore_compaction_deferred_directories() raises → _mark_background_compaction_failure(pending_recovery=True) is skipped → ensure_services() never raises CompactionError → deferred files are gone with no indication of failure.

Fix — wrap restore calls in inner try/except

            # BEFORE (lines 1402-1418):
            if retryable_directories:
                await self.realtime_indexing.restore_compaction_deferred_directories(
                    retryable_directories
                )
            if restore_files:
                await self.realtime_indexing.restore_compaction_deferred_files(
                    restore_files
                )
            if retryable_removals:
                await self.realtime_indexing.restore_compaction_deferred_removals(
                    retryable_removals
                )
            self._mark_background_compaction_failure(
                e, pending_recovery=True, retry_attempted=is_recovery_retry,
            )

            # AFTER:
            try:
                if retryable_directories:
                    await self.realtime_indexing.restore_compaction_deferred_directories(
                        retryable_directories
                    )
                if restore_files:
                    await self.realtime_indexing.restore_compaction_deferred_files(
                        restore_files
                    )
                if retryable_removals:
                    await self.realtime_indexing.restore_compaction_deferred_removals(
                        retryable_removals
                    )
            except Exception as restore_exc:
                failure_detail += f"; restore also failed: {restore_exc}"
            # _mark_background_compaction_failure NOW ALWAYS RUNS:
            self._mark_background_compaction_failure(
                e, pending_recovery=True, retry_attempted=is_recovery_retry,
            )
The final raise at line 1424 re-raises the original exception e — Python's raise inside except Exception as e: always re-raises the bound exception, not any exception from the inner try.

Issue 5 — Connection Gate Opens Before Reconnect Completes Important

File: chunkhound/providers/database/duckdb_provider.py  ·  lines 4400–4410

Problem

_restore_connection_after_compaction opens the connection gate (_connection_allowed.set()) before calling connect(). If connect() raises — particularly in the error-recovery path after a failed swap — the gate is permanently open with no working connection. Concurrent MCP requests pass the gate check (is_accepting_connections) but hit a dead or inconsistent database.

# CURRENT (broken order):
def _restore_connection_after_compaction(self) -> None:
    if self.terminal_after_stuck_cleanup:
        raise CompactionError(...)
    self._connection_allowed.set()   # gate OPENS  ← line 4409
    self.connect()                   # connect (can raise!)  ← line 4410
    # If connect() raises here: gate is open, connection is broken
The finally block at lines 4397–4398 only sets the gate if is_connected — it never clears a gate that was prematurely opened. Once set() is called, there is no recovery path that closes it back.

Fix — connect first, then open gate

def _restore_connection_after_compaction(self) -> None:
    """Reconnect after compaction unless cleanup has made the provider terminal.

    connect() is called before opening the gate so that if connect() raises,
    the gate stays closed — concurrent requests will receive CompactionError
    rather than hitting a broken provider with an open gate.
    """
    if self.terminal_after_stuck_cleanup:
        raise CompactionError(
            "Compaction cannot restore the database connection after terminal "
            "stuck-cleanup state",
            operation="compaction",
            recoverable=False,
        )
    self.connect()                   # connect first — gate stays closed if this raises
    self._connection_allowed.set()   # only open gate after successful connect
The finally block's if self.is_connected: self._connection_allowed.set() is idempotent on double-set — calling threading.Event.set() twice is a no-op. No regression risk from the safety net.
