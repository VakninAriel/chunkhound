01 What Is ChunkHound?

ChunkHound is a semantic and regex code search engine that transforms a codebase into a searchable knowledge base for AI assistants. It parses source files, extracts semantic chunks (functions, classes, etc.), generates vector embeddings, and exposes the results via a CLI and an MCP (Model Context Protocol) server.

Key fact: 100% of this code was written by AI agents — zero human-authored lines. The project is deliberately self-documenting through naming and structure.

What it does end-to-end

  1. Index — Walk a directory, parse files with tree-sitter, split into semantic chunks
  2. Embed — Send chunks to an embedding provider (OpenAI, VoyageAI) to generate vectors
  3. Store — Persist files, chunks, and vectors in DuckDB (or LanceDB)
  4. Search — Accept a natural-language query, embed it, run ANN vector search, return ranked chunks
  5. Serve — Expose search & index as MCP tools so AI assistants (Claude, Cursor, etc.) can call them

Who uses it

  • AI coding assistants needing codebase context (via MCP protocol)
  • Developers searching their own repos semantically from the CLI
  • Automated agents running multi-hop code research

04 Domain Models

Three frozen dataclasses form the core of every operation. All are immutable — mutation is handled by creating new instances.

File — represents a source file 
@dataclass(frozen=True)
class File:
    path: FilePath          # relative path (str alias)
    mtime: Timestamp        # unix timestamp
    language: Language      # enum — 32 supported + UNKNOWN
    size_bytes: int
    id: FileId | None = None

Used for: change detection (mtime), language routing, file-level metadata.

Chunk — a semantic code unit 
@dataclass(frozen=True)
class Chunk:
    symbol: str               # function/class name
    start_line: LineNumber    # 1-based
    end_line: LineNumber      # 1-based, inclusive
    code: str                 # raw source text
    chunk_type: ChunkType     # function, class, method, header_1 …
    file_id: FileId
    language: Language
    id: ChunkId | None = None
    parent_header: str | None = None  # markdown heading context

The fundamental retrieval unit. Every embedding points to one chunk.

Embedding — a vector for one chunk 
@dataclass(frozen=True)
class Embedding:
    chunk_id: ChunkId
    provider: ProviderName   # "openai", "voyageai"
    model: ModelName         # "text-embedding-3-small"
    dims: Dimensions         # 1536, 3072, 1024 …
    vector: list[float]
    created_at: datetime | None

Stored in the DB as the HNSW vector index entry.

05 Configuration System

All config is Pydantic-validated. Multiple sources are merged in strict precedence order.

Precedence (highest → lowest)

  1. CLI arguments (e.g. --db, --no-embeddings)
  2. .chunkhound.json in the target directory
  3. File passed via --config
  4. Environment variables (CHUNKHOUND_*)
  5. Global config file — auto-discovered in order (see below)
  6. Hard-coded defaults

Global config file (new)

A machine-wide config is loaded before project-local files. ChunkHound searches these 6 paths in order, using the first found:

1. $CHUNKHOUND_GLOBAL_CONFIG_FILE   (env var override)
2. ~/.config/chunkhound/chunkhound.json
3. ~/.config/chunkhound/config.json
4. ~/.chunkhound/config.json
5. ~/.chunkhound.json
6. /etc/chunkhound/config.json

This allows setting a default embedding API key or model for all projects on a machine without touching each project's .chunkhound.json.

Gotcha: --config does NOT override a project-local .chunkhound.json for the DB path. Use explicit --db when the target project has its own config.

Config structure

07 Indexing Pipeline

Entry point: services/indexing_coordinator.py — IndexingCoordinator.process_directory()

5-phase pipeline

Phase 1: Discovery
  Walk directory → detect language → filter .gitignore → return file list

Phase 2: Parallel Parsing  (CPU-bound, ProcessPoolExecutor, 4–16 workers)
  Each file → UniversalParser → ParseResult{chunks[]}
  Chunk diffing: if file hash unchanged → skip reparse (10× speedup)

Phase 3: Chunking — CAST Algorithm
  tree-sitter generates AST → ChunkSplitter traverses tree
  Extracts semantic units at natural boundaries (functions, classes, etc.)
  Preserves hierarchy; smart line-range assignment

Phase 4: Embedding Generation  (async, semaphore-limited)
  Batch chunks by token count + provider limits
  Check existing embeddings — skip unchanged chunks
  Rate-limited API calls with concurrency cap

Phase 5: Database Storage  (serial, single-thread executor)
  Transaction batches of 5000 records
  Insert: files → chunks → embeddings
  Rebuild HNSW vector index if >50 new embeddings
Key optimization: chunk diffing

Before re-parsing a file, the coordinator computes a hash of the file content and compares it to the stored hash. If unchanged, the entire parse/embed/store cycle is skipped for that file. This gives roughly a 10× speedup on incremental re-indexing of large repos.

Parallelism model

Parsing is CPU-bound → ProcessPoolExecutor with 4–16 workers (scales with file count).

Embedding is I/O-bound → asyncio with a semaphore limiting concurrent API batches (auto-detected per provider).

Database writes are serial → single _db_thread executor to avoid DuckDB connection conflicts.

08 Search Pipeline

Entry point: services/search_service.py — SearchService.search_semantic() or .search_regex()

Semantic search flow

  1. Embed query — call the configured embedding provider on the query string
  2. Strategy selection — single-hop (default) or multi-hop (when provider supports reranking)
  3. Vector search — HNSW cosine similarity (DuckDB) or IVF (LanceDB); returns top-K chunks
  4. Result enhancement — attach file paths, scores, surrounding context lines
  5. Return — ranked list of Chunks with similarity scores

Multi-hop search (research mode)

  1. Initial broad vector search
  2. Expand from results (follow symbol references)
  3. Rerank with VoyageAI rerank-2 model
  4. Retrieve surrounding context (ContextRetriever)

Regex search (no embeddings needed)

  • LIKE-pattern match on chunk code text in the DB
  • Works fully offline — no API calls
  • Optional path filter, pagination supported
Regex search is the fastest way to verify your index is working. Run it first whenever debugging "zero results" issues.

09 Embedding System

Managed by services/embedding_service.py and embeddings.py (EmbeddingManager).

ProviderModelsDimsBatch sizeConcurrencyExtras
OpenAI text-embedding-3-small
text-embedding-3-large		 1536 / 3072 2000 texts 3 batches —
VoyageAI voyage-3 1024 128 texts 4 batches Reranking (rerank-2)

Batching strategy

  • Split chunk list by token count (provider token limit)
  • Further split by batch size (e.g. 1000 texts per batch)
  • Concurrent async calls limited by semaphore (auto-detected per provider)
  • Check DB for existing embeddings before calling API — skip unchanged chunks
AGENTS.md rule: Always batch embeddings — minimum 100, maximum provider limit. Never make single-row DB inserts in loops.

All parsers live in chunkhound/parsers/. The primary parser is tree-sitter based, supporting 32 languages via a unified interface.

CAST algorithm — what makes it special

  • Operates on the syntax tree, not line counts
  • Respects language-specific semantic boundaries (function body, class block, etc.)
  • Preserves hierarchy — nested classes/functions get separate chunks
  • Codepoint-aware: handles multi-byte Unicode correctly in line ranges
  • Output: chunks that are meaningful to both LLMs and vector search

Language support

11 Database Layer

Two backends are supported. DuckDB is the default and primary target. All DB access goes through a serial executor wrapper — one thread, no connection conflicts.

DuckDB (primary)

  • Path: .chunkhound/db/chunks.db
  • HNSW vector index via vss extension
  • WAL mode, 1 GB checkpoint limit
  • Provider: providers/database/duckdb_provider.py

LanceDB (alternative)

  • Path: .chunkhound/db/lancedb.lancedb/ (directory)
  • IVF index for vector search
  • Better for very large indexes
  • Provider: providers/database/lancedb_provider.py

Repository layer (DuckDB)

ClassFileResponsibility
DuckDBFileRepositoryduckdb/file_repository.pyFile CRUD, change detection via content_hash
DuckDBChunkRepositoryduckdb/chunk_repository.pyChunk CRUD, line-range overlap queries, text LIKE search
DuckDBEmbeddingRepositoryduckdb/embedding_repository.pyEmbedding CRUD, upsert by (chunk_id, provider, model), HNSW vector search
DuckDBConnectionManagerduckdb/connection_manager.pyConnection pooling, WAL validation + corruption recovery, extension loading

Serial execution — the critical pattern

providers/database/serial_database_provider.py wraps any DB provider with a single-threaded executor (ThreadPoolExecutor(max_workers=1)). Every DB call is submitted as a future and awaited. This prevents DuckDB connection conflicts from concurrent async tasks.

DB path gotcha: Always pass the directory to --db, not the file. --db .chunkhound/db is correct; --db .chunkhound/db/chunks.db creates a nested chunks.db/chunks.db directory and silently returns zero results.

11b Database Schema

ChunkHound uses four tables. The embedding table is created per vector dimension (e.g., embeddings_1536, embeddings_1024) so different models can coexist without schema changes.

schema_version — migration tracking 
CREATE TABLE IF NOT EXISTS schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    description TEXT
);
files — source file metadata 
CREATE SEQUENCE IF NOT EXISTS files_id_seq;

CREATE TABLE IF NOT EXISTS files (
    id           INTEGER PRIMARY KEY DEFAULT nextval('files_id_seq'),
    path         TEXT UNIQUE NOT NULL,   -- relative path (the lookup key)
    name         TEXT NOT NULL,
    extension    TEXT,
    size         INTEGER,
    modified_time TIMESTAMP,
    content_hash TEXT,                   -- used for change detection / chunk diffing
    language     TEXT,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_files_path     ON files(path);
CREATE INDEX IF NOT EXISTS idx_files_language ON files(language);
chunks — semantic code units 
CREATE SEQUENCE IF NOT EXISTS chunks_id_seq;

CREATE TABLE IF NOT EXISTS chunks (
    id          INTEGER PRIMARY KEY DEFAULT nextval('chunks_id_seq'),
    file_id     INTEGER REFERENCES files(id),   -- FK to files table
    chunk_type  TEXT NOT NULL,                  -- ChunkType enum value
    symbol      TEXT,                           -- function/class name
    code        TEXT NOT NULL,                  -- raw source text
    start_line  INTEGER,                        -- 1-based
    end_line    INTEGER,                        -- 1-based, inclusive
    start_byte  INTEGER,
    end_byte    INTEGER,
    language    TEXT,
    metadata    TEXT,                           -- JSON serialized extras
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_chunks_file_id ON chunks(file_id);
CREATE INDEX IF NOT EXISTS idx_chunks_type    ON chunks(chunk_type);
CREATE INDEX IF NOT EXISTS idx_chunks_symbol  ON chunks(symbol);
embeddings_{dims} — per-dimension vector tables 
-- Created dynamically; one table per (dims) value encountered.
-- Example for 1536-dimensional OpenAI embeddings:

CREATE SEQUENCE IF NOT EXISTS embeddings_id_seq;

CREATE TABLE IF NOT EXISTS embeddings_1536 (
    id         INTEGER PRIMARY KEY DEFAULT nextval('embeddings_id_seq'),
    chunk_id   INTEGER NOT NULL,
    provider   TEXT NOT NULL,          -- "openai", "voyageai"
    model      TEXT NOT NULL,          -- "text-embedding-3-small"
    embedding  FLOAT[1536],            -- the vector (typed array)
    dims       INTEGER NOT NULL DEFAULT 1536,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Regular indexes
CREATE INDEX IF NOT EXISTS idx_1536_chunk_id        ON embeddings_1536(chunk_id);
CREATE INDEX IF NOT EXISTS idx_1536_provider_model  ON embeddings_1536(provider, model);

-- Uniqueness: one embedding per (chunk, provider, model) — enables upsert semantics
CREATE UNIQUE INDEX IF NOT EXISTS idx_1536_chunk_provider_model_unique
    ON embeddings_1536(chunk_id, provider, model);

-- HNSW vector index for ANN search (requires vss extension)
SET hnsw_enable_experimental_persistence = true;
CREATE INDEX IF NOT EXISTS idx_hnsw_1536
    ON embeddings_1536
    USING HNSW (embedding)
    WITH (metric = 'cosine');

-- Extension bootstrap (run once at startup)
INSTALL vss;
LOAD vss;
Why per-dimension tables? DuckDB's FLOAT[N] type is fixed-width. A 1536-dim vector cannot be stored in the same column as a 1024-dim vector. Separate tables also allow different HNSW indexes per model family with no cross-contamination.

Entity-relationship overview

files (1) ──── (N) chunks (1) ──── (N) embeddings_{dims}
  id ◄────────── file_id    id ◄──────── chunk_id

11c Main Queries

Vector search — the core semantic query 
-- Semantic nearest-neighbor search using HNSW cosine similarity.
-- The ARRAY[...] literal is the embedded query vector.
-- array_distance() with cosine returns 1 - similarity (lower = closer).

SELECT
    c.id        AS chunk_id,
    c.file_id,
    f.path      AS file_path,
    c.symbol,
    c.code,
    c.start_line,
    c.end_line,
    c.chunk_type,
    c.language,
    1 - array_distance(e.embedding, ARRAY[...]:FLOAT[1536]) AS score
FROM embeddings_1536 e
JOIN chunks  c ON e.chunk_id = c.id
JOIN files   f ON c.file_id  = f.id
WHERE e.provider = ?
  AND e.model    = ?
ORDER BY array_distance(e.embedding, ARRAY[...]:FLOAT[1536])
LIMIT ?;
Regex / text search — no embeddings required 
-- Pattern search using SQL LIKE (works offline, no API calls).
-- Path filter is optional.

SELECT
    c.id, c.file_id, f.path AS file_path,
    c.symbol, c.code, c.start_line, c.end_line,
    c.chunk_type, c.language
FROM chunks c
JOIN files f ON c.file_id = f.id
WHERE c.code LIKE ?              -- e.g. '%def search%'
  AND f.path LIKE ?              -- optional path filter
ORDER BY f.path, c.start_line
LIMIT ?
OFFSET ?;
File CRUD — insert, get, update 
-- Insert new file (returns generated id)
INSERT INTO files (path, name, extension, size, modified_time, content_hash, language)
VALUES (?, ?, ?, ?, to_timestamp(?), ?, ?)
RETURNING id;

SELECT id, path, name, extension, size, modified_time, language, content_hash,

FROM files
WHERE path = ?;

-- Update after re-index (bump mtime + hash for change detection)
UPDATE files
SET    size          = ?,
       modified_time = to_timestamp(?),
       content_hash  = ?,
       updated_at    = CURRENT_TIMESTAMP
WHERE  id = ?;
Chunk queries — batch insert + range lookup 
-- Bulk insert (batches of up to 1000 rows per statement)
INSERT INTO chunks (file_id, chunk_type, symbol, code,
                   start_line, end_line, start_byte, end_byte, language, metadata)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?),
       (?, ?, ?, ?, ?, ?, ?, ?, ?, ?),
       ...
RETURNING id;

-- Get all chunks for a file (used for chunk diffing before re-index)
SELECT id, file_id, chunk_type, symbol, code,
       start_line, end_line, start_byte, end_byte, language, metadata
FROM chunks
WHERE file_id = ?
ORDER BY start_line;

-- Overlap query — find chunks touching a line range
SELECT id, file_id, chunk_type, symbol, code, start_line, end_line, language
FROM chunks
WHERE file_id = ?
  AND (
      (start_line BETWEEN ? AND ?) OR
      (end_line   BETWEEN ? AND ?) OR
      (start_line <= ? AND end_line >= ?)   -- chunk spans the entire range
  )
ORDER BY start_line;
Embedding upsert + existence check 
-- Upsert: insert or update if (chunk_id, provider, model) already exists
INSERT INTO embeddings_1536 (chunk_id, provider, model, embedding, dims)
VALUES (?, ?, ?, ?, ?)
ON CONFLICT (chunk_id, provider, model) DO UPDATE
SET embedding = EXCLUDED.embedding,
    dims      = EXCLUDED.dims;

-- Bulk existence check before calling the embedding API
-- (avoids re-embedding chunks that already have vectors)
SELECT DISTINCT chunk_id
FROM embeddings_1536
WHERE chunk_id IN (?, ?, ?, ...)
  AND provider = ?
  AND model    = ?;
Cascade delete — remove a file and all its data 
-- Step 1: delete embeddings for all chunks belonging to the file
DELETE FROM embeddings_1536
WHERE chunk_id IN (SELECT id FROM chunks WHERE file_id = ?);

-- Step 2: delete the chunks
DELETE FROM chunks WHERE file_id = ?;

-- Step 3: delete the file record
DELETE FROM files WHERE id = ?;
No foreign-key CASCADE is defined — the application performs manual three-step deletion to keep control over HNSW index safety.
HNSW index management — drop/recreate for bulk inserts 
-- Drop HNSW index before a large bulk insert (10-20× faster)
DROP INDEX IF EXISTS idx_hnsw_1536;

-- ... bulk INSERT embeddings here ...

-- Recreate HNSW after bulk insert
SET hnsw_enable_experimental_persistence = true;
CREATE INDEX idx_hnsw_1536
    ON embeddings_1536
    USING HNSW (embedding)
    WITH (metric = 'cosine');

-- Threshold: drop/recreate only when inserting > 50 embeddings.
-- Below that threshold the overhead outweighs the gain.
Statistics & introspection queries 
-- Count all indexed entities
SELECT COUNT(*) FROM files;
SELECT COUNT(*) FROM chunks;
SELECT COUNT(*) FROM embeddings_1536;

-- Which embedding tables exist (introspect all dims in use)
SELECT table_name
FROM information_schema.tables
WHERE table_name LIKE 'embeddings_%';

-- List HNSW indexes
SELECT index_name, table_name, sql
FROM duckdb_indexes()
WHERE table_name LIKE 'embeddings_%';

-- Check schema version
SELECT MAX(version) FROM schema_version;

-- Chunk type distribution for a file
SELECT chunk_type, COUNT(*) AS count
FROM chunks
WHERE file_id = ?
GROUP BY chunk_type;

Query performance rules

  • Vector search: always hits the HNSW index — O(log N) even at millions of rows
  • File lookup by path: hits idx_files_path — effectively O(1)
  • Chunk lookup by file: hits idx_chunks_file_id — O(chunks-per-file)
  • Regex search: sequential scan on chunks.code — slow on large DBs; add LIMIT
  • Bulk inserts: always batch ≥100 rows; drop HNSW index first when inserting >50 embeddings

12 MCP Server

ChunkHound exposes its capabilities as MCP (Model Context Protocol) tools so AI assistants can call them programmatically.

Two transport modes

Stdio (mcp_server/stdio.py)

  • JSON-RPC over stdin/stdout
  • NEVER use print() — breaks the protocol
  • All logging forced to CRITICAL level
  • Used by Claude Code, Cursor, Zed, VS Code MCP extensions
  • Start: uv run chunkhound mcp
  • --read-only flag: forces single-process stdio, sets DatabaseConfig.read_only=True. Env var: CHUNKHOUND_DATABASE__READ_ONLY=true. Use when the DB is managed by a separate indexer process and the MCP server should never write.

HTTP (mcp_server/http_server.py)

  • Starlette ASGI server
  • SSE (Server-Sent Events) for streaming
  • WebSocket support
  • Start: uv run chunkhound mcp http --port 5173

MCP Tools — 4 tools registered

Tool nameRequiresWhat it doesKey parameters
search embeddings (for semantic only) Unified regex + semantic search. type="regex" runs LIKE pattern match; type="semantic" runs HNSW vector search via multi-hop. Returns lean markdown (e.g. ## filepath L10–L20 — symbol (92%)) instead of raw JSON. type, query, path, page_size, offset
code_research embeddings + LLM + reranker Deep BFS research — calls UnifiedSearch up to 4×, extracts symbols, runs regex augmentation, LLM synthesises a cited markdown report. The main entry point for architecture questions. query, path
daemon_status none Reports daemon health: whether initial indexing has completed, scan progress, and realtime indexing state. Use to check if the index is query-ready. (none)
websearch internet access (DuckDuckGo) New. Searches the web via DuckDuckGo, fetches result pages, builds an in-memory ChunkHound index from the content, runs deep research against that index, and returns a synthesised markdown report. Note: The original guide listed index, get_indexed_files, get_stats, and research as MCP tools — these do not exist in the current codebase. Indexing is triggered via the CLI (chunkhound index), not via MCP. The research tool is named code_research, not research.

Tool definition pattern

Tools are declared in mcp_server/tools.py using a @register_tool() decorator. JSON Schema is auto-generated from the Python function signature and docstring. The decorator registers each tool into a TOOL_REGISTRY dict — this is the single source of truth, no manual schema maintenance.

@register_tool(
    description=SEARCH_DESCRIPTION,
    requires_embeddings=False,
    name="search",
)
async def search_impl(
    services: DatabaseServices,
    embedding_manager: EmbeddingManager | None,
    type: Literal["regex", "semantic"],
    query: str,
    path: str | None = None,
    page_size: int = 10,
    offset: int = 0,
) -> SearchResponse: ...

14 Design Patterns

Pattern 1 — Immutable domain models

File, Chunk, Embedding are @dataclass(frozen=True). Validation in __post_init__. Safe to cache, share across threads, and use as dict keys.

Pattern 2 — Protocol-based abstraction (structural typing)

DatabaseProvider, EmbeddingProvider, LLMProvider, LanguageParser are Python Protocols. Any class with matching methods satisfies the interface — no inheritance required. Enables easy test mocking.

Pattern 3 — Serial database executor

SerialDatabaseProvider wraps any provider in a single ThreadPoolExecutor(max_workers=1). All DB calls are submitted as futures and awaited. This prevents DuckDB connection conflicts from concurrent threads.

Pattern 4 — Lazy language parser loading

LazyLanguageParsers in the registry instantiates parsers on first access and caches them. Reduces startup time — you don't pay the cost of loading a tree-sitter grammar for Ruby if you never index Ruby files.

Pattern 5 — Chunk diffing

Before reprocessing, the indexing coordinator hashes file content and compares to the stored hash. Unchanged files skip parse → embed → store entirely. ~10× speedup for incremental re-indexing.

Pattern 6 — Process pool for CPU-bound, async for I/O-bound

Parsing uses ProcessPoolExecutor (true parallelism, bypasses GIL). Embedding API calls use asyncio with semaphore-limited concurrency. DB writes use a serial executor. Each bottleneck gets the right model.

Pattern 7 — Declarative MCP tools

Tool definitions in tools.py generate JSON Schema automatically from Python type hints. No manual schema maintenance. One function signature = one MCP tool definition.

Pattern 8 — Configuration as Pydantic models

All config structures are BaseModel subclasses. Multiple sources (CLI args, JSON files, env vars) merged in precedence order by the config loader. Invalid configs raise on startup, not at runtime.

16 Registry & Dependency Injection

File: chunkhound/registry/__init__.py — ProviderRegistry

The registry is the composition root — it wires all providers, services, and parsers together. It is instantiated once per process and passed to services.

What the registry manages

  • Database provider (creates and wraps in SerialDatabaseProvider)
  • Embedding provider (selected by config)
  • LLM provider (selected by config)
  • Language parsers (lazy-loaded, cached)
  • Service instances (IndexingCoordinator, SearchService, etc.)

Key methods

registry = ProviderRegistry(config)
registry.configure()                     # init all providers
provider = registry.get_provider()       # get DB provider
coord = registry.create_indexing_coordinator()
search = registry.create_search_service()

The composition flow: database_factory.py → creates ProviderRegistry → registry creates all services → services injected into CLI commands or MCP handlers.

19 Gotchas & Hard Rules

NEVER use print() in stdio.py, http_server.py, or tools.py — it corrupts the MCP JSON-RPC stream.
NEVER make single-row DB inserts in loops — always batch (min 100, max provider limit).
NEVER edit version strings manually — always use uv run scripts/update_version.py to create git tags.
DB path: Pass the directory to --db, not the .db file. Wrong path → silent zero results, no error.
Forward references: Avoid quoted type annotations ("MyClass") unless genuinely needed for circular imports.
uv everywhere: All Python operations must use uv run, uv add, etc. Never use bare pip or python.
Preferred DB resolution: Pass the project directory as a positional arg (chunkhound search "query" /path/to/project) — this reads .chunkhound.json automatically. The --db flag is for edge cases.

21 New Features (Latest Release)

56 commits landed on main since the initial guide was written. Here are the 7 most significant additions, with the key design decisions explained.

1. DB Compaction

Over time, deleted chunks leave gaps in the DuckDB file and the HNSW vector index. Compaction reclaims that space atomically so queries stay fast.

Protocol: HNSW Bookend — drop the HNSW index before copying data, then rebuild it on the compacted DB. HNSW is an in-memory structure; it cannot be streamed across databases.

# Internal stages (chunkhound/providers/database/compaction/)
_compact_prepare()   # create a fresh empty DB
_compact_copy_data() # bulk INSERT … SELECT all live chunks/embeddings
_compact_finalize()  # atomic rename: new DB replaces old DB
_compact_restore()   # if anything fails, restore original

had_hnsw = drop_hnsw_index()   # remember whether HNSW existed
copy_data()                     # copy without HNSW
if had_hnsw: rebuild_hnsw()    # rebuild on the compacted copy

Fragmentation monitoring runs after every delete batch. A compaction is triggered automatically when fragmentation exceeds the configured threshold.

2. Git-Diff Semantic Search

ChunkHound can now index and search git diffs as semantic chunks, not just static source files.

  • New module: chunkhound/core/git_diff/
  • New language constant: Language.GIT_DIFF
  • New chunk type: ChunkType.GIT_DIFF
  • Service: DiffAwareSearchService — wraps the existing search stack with diff-aware context injection

Three search modes:

ModeWhat it searches
dbOnly the indexed codebase (default, unchanged behaviour)
diffOnly the current git diff output
bothMerges results from the DB index and the live diff, reranked together

Use case: "what did this PR change that relates to authentication?" — pass mode=diff and search the diff directly without re-indexing.

3. Global Config File

See the updated Section 5 — Configuration System above. Machine-wide defaults (API keys, default model) are now supported through a global config file at ~/.config/chunkhound/chunkhound.json. This avoids repeating API key configuration in every project's .chunkhound.json.

4. MCP --read-only Flag

The MCP server now accepts --read-only, setting DatabaseConfig.read_only = True. When enabled:

  • Forces single-process stdio mode (no background writer threads)
  • All DB write paths assert-fail, preventing accidental corruption
  • The daemon watcher is not started — saves memory in read-only deployments
  • Env var shorthand: CHUNKHOUND_DATABASE__READ_ONLY=true

Typical pattern: run chunkhound index as a CI step, then serve the frozen DB via MCP with --read-only.

5. Rust-Native File Scanner (chunkhound_native)

File discovery (walking the directory tree, applying .gitignore rules) was previously done in Python. It is now optionally offloaded to a Rust extension module for large repos.

  • Extension: chunkhound_native (PyO3-based, installed as a wheel)
  • Source: chunkhound_native/ directory (Rust crate)
  • Uses the Rust ignore crate for parallel directory walking + full .gitignore semantics
  • Entry point: scan_files(root: str, exclude_patterns: list[str]) → list[str]
  • The Python scanner remains as a fallback if the native extension is not installed

On a 500k-file monorepo the native scanner is ~10× faster than os.walk.

6. WebSearch MCP Tool

See the updated Section 12 — MCP Server. The new websearch tool lets MCP clients search the web without leaving the tool interface:

  1. Query DuckDuckGo for URLs
  2. Fetch and extract text from result pages
  3. Build an in-memory ChunkHound index from the fetched content
  4. Run the full code_research deep-research pipeline against that index
  5. Return a synthesised markdown report with citations

Parameters: query (required), limit (number of pages to fetch, default 5), path_filter (domain filter).
