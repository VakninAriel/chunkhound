⚠️ The Problem

DuckDB databases grow fragmented over time. Every time ChunkHound indexes a codebase — inserting chunks, updating embeddings, deleting stale files — DuckDB accumulates reclaimable space in two forms:

  • Free blocks: Block-level space from dropped indexes and CHECKPOINT cycles that DuckDB cannot coalesce into reusable storage
  • Row-group waste: Partially-deleted row groups where rows were removed but the underlying Parquet blocks on disk are still allocated

DuckDB's built-in CHECKPOINT (also called VACUUM) only reclaims space when ≥25% of rows in adjacent row groups are deleted — a threshold that is rarely met in practice for incremental indexing workloads. The result: disk usage grows monotonically, never shrinking, even after large-scale deletions.

Root cause: DuckDB has no in-place compaction. The only way to fully reclaim all fragmented space is to export the database to fresh Parquet files and re-import into a new, empty database file — the same approach used by VACUUM FULL in PostgreSQL.
How fragmentation was measured

Two metrics are tracked and combined into an effective_waste signal:

# chunkhound/services/compaction_service.py
def estimate_reclaimable_bytes(stats: dict[str, Any]) -> int:
    block_size   = stats.get("block_size", 262144)   # 256KB default
    free_blocks  = stats.get("free_blocks", 0)
    used_blocks  = stats.get("used_blocks", 0)
    row_waste    = stats.get("row_waste_ratio", 0.0)
    # max() catches block-level OR row-group fragmentation
    return int(max(
        free_blocks * block_size,
        int(row_waste * used_blocks * block_size),
    ))

effective_waste = max(free_ratio, row_waste_ratio) — both signals trigger compaction independently so neither type of fragmentation is missed.

💡 Solution Design

The compaction system has three user-facing surfaces and one internal safety layer:

🖥️ chunkhound repack CLI

  • --dry-run previews reclaimable space
  • --backup saves a copy before compacting
  • Human-readable before/after size report
  • Checks provider type first (DuckDB only)

🤖 Background MCP Auto-Compaction

  • Triggers after initial scan when waste > threshold
  • Non-blocking — MCP tool calls continue during compaction
  • Post-compaction force-reindex callback
  • Failed state cleared after successful reindex

🔒 Connection Gate

  • Blocks DB queries during the swap window
  • MCP clients receive structured CompactionError
  • Retry hint included in error response
  • Gate released immediately after swap completes

📋 Configurable Thresholds

  • CHUNKHOUND_DATABASE__COMPACTION_ENABLED
  • CHUNKHOUND_DATABASE__COMPACTION_THRESHOLD (0.0–1.0)
  • CHUNKHOUND_DATABASE__COMPACTION_MIN_SIZE_MB
  • Invalid values warn-and-skip, never crash

Step 5 is the only crash-unsafe window. Two os.replace() calls are used — POSIX-atomic on all major Linux filesystems. The intent-file protocol (below) ensures recovery from any crash between these calls.
EXPORT/IMPORT implementation (simplified) 
# chunkhound/providers/database/duckdb_provider.py
def _run_blocking_compaction(self, db_path):
    # 1. Disk preflight — require 3× current size free
    free_bytes = shutil.disk_usage(db_path.parent).free
    if free_bytes < db_path.stat().st_size * 3.0:
        raise CompactionError("insufficient disk space")

    # 2. Capture HNSW metadata before disconnecting
    hnsw_indexes = self._capture_hnsw_indexes_from_conn(conn)

    # 3. EXPORT to temp dir
    safe = self._sql_literal_path(export_dir)
    conn.execute(f"EXPORT DATABASE '{safe}' (FORMAT PARQUET)")

    # 4. IMPORT into fresh file
    import_conn = duckdb.connect(str(compact_db))
    import_conn.execute(f"IMPORT DATABASE '{safe}'")

    # 5. Recreate HNSW indexes (DuckDB doesn't export them)
    self._recreate_hnsw_indexes_in_conn(import_conn, hnsw_indexes)
    import_conn.execute("CHECKPOINT")

    # 6. Write intent file, then atomic swap
    intent.write_text("phase2")
    os.replace(db_path, old_db)      # rename original → .old
    os.replace(compact_db, db_path)  # rename compact → live

🔍 HNSW Vector Index Preservation

DuckDB's EXPORT DATABASE does not export HNSW vector similarity indexes — they exist only in the database's internal catalog and are silently dropped during export. Without intervention, all vector search capability is lost after compaction.

Solution: Snapshot → Drop → Recreate

  1. Before export: query duckdb_indexes() to capture all HNSW index metadata (name, table, column, metric)
  2. After import: recreate each index using CREATE INDEX … USING HNSW with the captured metric parameter
  3. After recreation: CHECKPOINT to persist to the compacted file
Key fix applied in this session: The original implementation used _is_safe_duckdb_identifier() (regex [A-Za-z0-9_]*) to guard index names before recreation. This silently dropped any index whose name contained a hyphen — e.g. indexes created when model names like text-embedding-3-small were not yet sanitized. Both recreation paths now skip this guard and rely on _quote_duckdb_identifier() which safely double-quotes any name.
HNSW capture and recreate (simplified) 
# Capture before export
def _capture_hnsw_indexes_from_conn(self, conn):
    rows = conn.execute("""
        SELECT index_name, table_name, index_type
        FROM duckdb_indexes()
        WHERE index_type = 'HNSW'
    """).fetchall()
    return [{"index_name": r[0], "table_name": r[1]} for r in rows]

# Recreate after import (no _is_safe_duckdb_identifier guard)
def _recreate_hnsw_indexes_in_conn(self, conn, hnsw_indexes):
    for idx in hnsw_indexes:
        name = self._quote_duckdb_identifier(idx["index_name"])
        tbl  = self._quote_duckdb_identifier(idx["table_name"])
        conn.execute(f"""
            CREATE INDEX IF NOT EXISTS {name}
            ON {tbl} USING HNSW (embedding)
            WITH (metric = '{metric}')
        """)

🛡️ Crash Recovery Protocol

A crash can occur at any point in the compaction cycle. The intent-file protocol ensures the database is always in a usable state when the process restarts.

Crash DuringIntent File StateFiles PresentRecovery Action
Export / Import pre_swap Original intact Delete compact artifacts, open original
First os.replace phase1 original.old + compact.duckdb Complete swap: rename compact → live
Second os.replace phase2 old exists, live may be missing Probe compact; restore from .old if probe fails
After swap No intent file Live + .old Open live, delete .old
Foreign process compacting Foreign lock Lock file exists Raise CompactionError — do not interfere
Recovery logic in DuckDBConnectionManager 
# chunkhound/providers/database/duckdb/connection_manager.py
def _recover_from_interrupted_compaction(self):
    intent = self.db_path.with_suffix(".compact.intent")
    old_db = self.db_path.with_suffix(".duckdb.old")
    compact_db = self.db_path.with_suffix(".compact.duckdb")

    phase = intent.read_text().strip() if intent.exists() else ""

    if phase == "phase2":
        # First rename completed; ensure second also completed
        if not self.db_path.exists() and compact_db.exists():
            os.replace(compact_db, self.db_path)  # finish the swap
        elif not self.db_path.exists() and old_db.exists():
            os.replace(old_db, self.db_path)       # roll back

    elif phase in ("pre_swap", "phase1"):
        # Compaction did not complete — restore original
        if old_db.exists():
            os.replace(old_db, self.db_path)

🔐 Concurrency Safety

Four layers prevent concurrent access from corrupting the database during compaction:

1. Process-wide Registry

_COMPACTING_PATHS: set[str] is a module-level set protected by a threading.Lock. Any second DuckDBProvider instance pointing at the same database path within the same process will see the path in the registry and refuse to treat the active lock as stale.

2. Foreign Lock Detection (cross-process)

The compaction lock file embeds the writing process's PID and a boot-time timestamp. On connect, if a lock file is found and its PID is not the current process, the boot timestamp is compared against /proc/[pid]/stat to determine if the process is actually alive. A live foreign lock raises CompactionError(operation="connection") — the connecting process is rejected.

3. Atomic Check-and-Set

_try_start_compaction() acquires a threading.Lock to check and set _compaction_in_progress atomically — no TOCTOU race between eligibility check and flag set.

4. Connection Gate

_connection_allowed: threading.Event is cleared before the export begins and set after reconnect completes. The serial executor checks this event on every DB operation — any tool call that arrives during the swap window blocks until the gate opens.
