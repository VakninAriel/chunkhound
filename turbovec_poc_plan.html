TurboVec POC — Standalone Feasibility Benchmark Plan

Repo: my_chunkhound | Base branch: main | Scope: benchmark only, no production changes

Context

turbovec_integration_design_report.html (untracked at repo root) proposes replacing DuckDB-VSS/HNSW with the turbovec Rust crate (Google's TurboQuant algorithm) for quantized vector storage/search — claiming 16x compression at 4-bit, ~0.997 recall@1, and a way to reload a search index at startup from a serialized blob with zero re-embedding. That's a 2–3 week production migration across 4 phases, so before committing to it we want a standalone POC that validates the load-bearing technical claims on real data, with no changes to production code, schema, or the chunkhound_native PyO3 surface.

Two prior research passes covered the groundwork:

  • Located and summarized the design doc and its lineage — it assumes the unmerged feat/thin-rust-embed-pipeline branch, but this POC is built on main instead, decoupled from that branch.
  • Mapped the current architecture: DuckDB tables embeddings_{dims} + the vss extension's HNSW index, searched via duckdb_provider.py:3875 search_semantic(); chunkhound_native's RustDbWriter has no search method today; no turbovec reference exists anywhere in the codebase yet.
  • Verified the actual turbovec v0.9.0 crate API against its real source (not just the design doc's sketch), surfacing two corrections:
Correction 1 — no free from_parts() on IdMapIndex. Only the inner TurboQuantIndex has from_parts(), and it's id-less (positional only). The real whole-index reconstruction path is IdMapIndex::to_bytes()/from_bytes() — a full blob roundtrip. Reconstructing from decomposed per-vector parts (the design doc's embeddings_quantized fallback) requires hand-rolling an id-mapping layer on top of TurboQuantIndex::from_parts() — not free. The POC tests both paths explicitly so this is proven, not assumed.
Correction 2 — 4-bit compression is ~8x, not 16x. 1536 × 4 / 8 = 768 bytes, not 384. The design doc's 16x figure is actually the 2-bit number. The POC's compression measurement surfaces the real ratio.

The POC's job: produce trustworthy numbers on real data (not synthetic vectors) for compression, recall, latency, and the serialize/reload roundtrip, then decide go/no-go before anyone invests in the full migration.

Where It Lives

test-crates/turbovec-poc/ — a fully standalone Rust crate with its own Cargo.toml, entirely decoupled from chunkhound_native (which has no [workspace] table, so a nested crate here never touches its Cargo.lock, dependency graph, abi3-py310 feature set, or DuckDB/PyO3 linkage). This is a throwaway spike: no schema changes, no new RustDbWriter methods, nothing touching the production build.

Gitignore correctionverified: test-crates/ is not wholly ignored — only target/ directories are (via the generic target/ rule in root .gitignore). git status currently shows !! test-crates/ only because the existing test-crates/embed-tests/ contains nothing but an ignored target/ dir. New tracked-looking files (Cargo.toml, src/*.rs, and especially a ~75MB fixture binary) would show up as untracked, not ignored. Add test-crates/turbovec-poc/.gitignore containing fixtures/ and target/ so the dumped embeddings and build artifacts never risk being staged.

No duckdb, no pyo3. turbovec 0.9.0's own deps (faer, ndarray, rayon, etc.) are all pure Rust — reachable via the corporate proxy's crates.io sparse index, no other network access needed.

Sourcing Real Data

This repo's own .chunkhound/db/chunks.db has a real corpus: table embeddings_256, 73,474 vectors, 256-dim (Matryoshka-reduced from 1536 per QWEN3_TUNING.md), provider='openai', model='qwen3-embedding-4b'. No 1536-dim table exists locally — the POC runs at 256-dim, a deviation from the design doc's headline numbers, but real clustered code-embedding vectors at 256-dim still exercise realistic recall characteristics far better than random vectors.

scripts/dump_embeddings.py

import duckdb, struct

con = duckdb.connect("/home/e119870/views/g/my_chunkhound/.chunkhound/db/chunks.db", read_only=True)
rows = con.execute("SELECT chunk_id, embedding FROM embeddings_256 ORDER BY id").fetchall()

with open("fixtures/embeddings_256.bin", "wb") as f:
    f.write(b"CHKNVEC1")
    f.write(struct.pack("<II", len(rows), 256))
    for chunk_id, emb in rows:
        f.write(struct.pack("<q", chunk_id))
        f.write(struct.pack(f"<{len(emb)}f", *emb))

read_only=True avoids the single-writer lock conflicting with any running daemon. The fixed little-endian layout means fixture.rs needs no parsing crate.

What the Benchmark Measures

src/main.rs runs the following stages in order and prints one results report:

  1. Compression: dim*4 bytes (float32) vs IdMapIndex::to_bytes().len() / n_vectors, for both bit_width=2 and bit_width=4.
  2. Recall@1 and Recall@10 of TurboVec search vs. exact brute-force cosine (bruteforce.rs, plain O(n·dim) loop, no DuckDB dependency) — using a held-out query sample (e.g. 500 vectors excluded from the index before building it, not self-matched against the corpus that contains them) so recall reflects real nearest-neighbor retrieval, not trivial self-match. Run for both bit-widths.
  3. Search latency: median/p95 queries/sec, TurboVec vs. brute-force, at the ~73K-vector scale (informational only — the real win is at 1M+ vectors, so treat as a sanity check, not a gate).
  4. to_bytes()/from_bytes() roundtrip: build index → serialize → drop → reconstruct → same query batch → assert byte-identical (scores, ids). This is the single most important claim — the whole "why Rust" rationale.
  5. TurboQuantIndex::from_parts() emulation: pull packed_codes()/scales()/tqplus_shift()/tqplus_scale() off the built index's inner TurboQuantIndex, reconstruct via from_parts(), hand-reattach ids via a parallel Vec<u64>, confirm search still matches. Report clearly whether this worked as the design doc assumed or needed the hand-rolled id layer (per Correction 1, expect the latter).
Why tests/roundtrip.rs is separate from the benchmark report

Stages 4 and 5 above are encoded as real #[test] assertions, not just printed numbers — they're correctness claims, not benchmarks. cargo test fails loudly if either roundtrip diverges, so the benchmark's other numbers can only be trusted once these pass.

Rust Conventions

  • #![forbid(unsafe_code)] at the top of main.rs even though outside the production build (turbovec's public API needs no unsafe).
  • No PyO3 boundary in this POC, so AGENTS.md's .unwrap() restriction doesn't apply — ordinary .unwrap()/.expect() is fine for this throwaway spike; note that explicitly in the POC's README so it's not mistaken for production style.
  • Still run cargo fmt and cargo clippy --all-targets -- -D warnings inside test-crates/turbovec-poc/ before calling it done.
  • cargo test must pass before trusting the benchmark numbers.
  • PATH="$HOME/.cargo/bin:$PATH" needed in a fresh shell (cargo/rustc installed but not on default PATH here).

Ordered Steps

  1. mkdir -p test-crates/turbovec-poc, add .gitignore (fixtures/, target/), Cargo.toml.
  2. cargo build once to confirm turbovec fetches cleanly through the proxy.
  3. Write and run scripts/dump_embeddings.py; confirm fixtures/embeddings_256.bin is ~75MB / 73,474 records.
  4. Implement fixture.rs (reader) and bruteforce.rs (ground truth).
  5. Implement metrics.rs (recall@k, latency, compression math).
  6. Implement main.rs: load fixture → hold out query sample → build IdMapIndex at both bit-widths → run all measurements → print report.
  7. Implement tests/roundtrip.rs for steps 4/5 correctness checks; cargo test must pass.
  8. cargo fmt, cargo clippy --all-targets -- -D warnings; fix warnings.
  9. cargo run --release --bin bench; capture real numbers; compare against thresholds; write go/no-go conclusion into the POC's README.md.
  10. If go: flag the two design-doc corrections (no IdMapIndex::from_parts(); ~8x not 16x at 4-bit) back before anyone commits to the full 4-phase migration.
