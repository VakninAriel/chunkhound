Replacing DuckDB-VSS with TurboVec
in the Native Rust Extension

Author: Ariel Vaknin  |  Branch: feat/thin-rust-embed-pipeline  |  Status: Evaluation

🎯 Overview

This proposal evaluates replacing ChunkHound's float32 vector storage and DuckDB-VSS HNSW search with TurboVec — a Rust vector index based on Google Research's TurboQuant algorithm (ICLR 2026). The integration is native Rust-to-Rust via ChunkHound's existing chunkhound-native extension crate, requiring no new Python dependencies.

⚠️ Problem Statement

ChunkHound stores embeddings as raw FLOAT[1536] / FLOAT[3072] arrays in DuckDB with an HNSW index provided by the experimental DuckDB-VSS extension. At scale, this creates two compounding problems:

ScaleChunksVector storage (float32 / 1536-dim)Impact
Single repo~50K~300 MBManageable
Monorepo / large project~500K~3 GBMemory pressure
Multi-repo index~5M~30 GBProhibitive

Additionally, DuckDB-VSS requires SET hnsw_enable_experimental_persistence = true, a brittle drop-and-rebuild lifecycle around every bulk insert, and crash-recovery code. These are maintenance liabilities.

⚡ What is TurboVec?

TurboVec (github.com/RyanCodrai/turbovec) is a Rust library implementing the TurboQuant algorithm from Google Research (ICLR 2026). It is a pure in-memory ANN index with file-based persistence.

Key Properties

PropertyDetail
AlgorithmTurboQuant: data-oblivious quantizer, no training phase, online ingest
Compression8× (2-bit) or 16× (4-bit) — 1536-dim float32: 6,144 B → 384 B at 4-bit
SearchHand-written SIMD: AVX-512BW (x86) · NEON (ARM) · scalar fallback
Speed vs FAISS FastScan+10–19% on ARM · competitive on x86 at 4-bit
Recall @ k=1 / 1536-dim / 4-bit0.997 — reaches 1.0 by k=4
FilteringIn-kernel uint64 allowlist — no post-filter overhead
Persistence.tvim file format — load on startup, no rebuild
LanguagePure Rust crate — cargo add turbovec
Python bindingsPyO3 — but from_parts() low-level API is Rust-only

Why Rust-native? TurboVec's Python API cannot reconstruct an index from raw quantized bytes. Only the Rust API exposes TurboQuantIndex::from_parts() — the essential call for loading a persisted index without re-embedding. ChunkHound already has a Rust extension, making this a natural fit.

💡 Core Insight — Why This Works

Previous approaches (TurboVec as a Python layer) all fail because they create an inescapable trilemma:

ConstraintPython approachRust approach
No re-embedding on startup❌ Must rebuild from float32 or API✅ from_parts() from packed bytes
Save disk & memory❌ Still needs float32 somewhere✅ Only packed codes stored
Low startup cost❌ API calls or heavy reconstruction✅ Single DuckDB BLOB read → index

The Rust approach: store the TurboVec packed quantized bytes per vector in DuckDB as the durable source of truth, and reconstruct the in-memory IdMapIndex at startup via TurboQuantIndex::from_parts() — no embedding API calls, no float32 anywhere.

🏗️ Proposed Architecture

Data Model Change

Remove: embeddings_1536, embeddings_3072 tables (float32 arrays + HNSW index)

Add:

-- Per-vector durable store (packed quantized codes)
embeddings_quantized (
    id           INTEGER PRIMARY KEY,
    chunk_id     INTEGER NOT NULL REFERENCES chunks(id),
    provider     TEXT NOT NULL,
    model        TEXT NOT NULL,
    dims         INTEGER NOT NULL,
    packed_codes BLOB NOT NULL,   -- TurboVec quantized bytes for this vector
    scale        REAL NOT NULL,   -- per-vector length-renormalization scalar
    UNIQUE (chunk_id, provider, model)
)

-- Warm index snapshot per (provider, model, dims) for fast startup
turbovec_indexes (
    id         INTEGER PRIMARY KEY,
    provider   TEXT NOT NULL,
    model      TEXT NOT NULL,
    dims       INTEGER NOT NULL,
    payload    BLOB NOT NULL,     -- TurboQuantIndex::to_bytes() output
    n_vectors  INTEGER NOT NULL,
    updated_at TIMESTAMP,
    UNIQUE (provider, model, dims)
)

Why two tables? turbovec_indexes is the fast-startup path — load one BLOB, get a live index. embeddings_quantized is the durable per-vector fallback — if the snapshot is stale or corrupt, rebuild from packed codes without any embedding API calls.

Index Lifecycle

1
Startup

Read turbovec_indexes BLOB → IdMapIndex::from_parts() → in-memory index ready. If BLOB missing: read embeddings_quantized row-by-row → rebuild. No embedding API calls ever.

2
Indexing (write path)

EmbedBatchFn returns Vec<f32> (unchanged). Rust normalizes + encodes via TurboVec. Packed codes + scale stored in embeddings_quantized (upsert). Vector added to in-memory IdMapIndex. At batch-end: serialize index → UPDATE turbovec_indexes SET payload=....

3
Search (query path)

Python calls RustDbWriter.search_semantic(query_vec, provider, model, k, path_filter). Rust encodes query (no DB read). If path_filter: SQL query for matching chunk_ids → uint64 allowlist. IdMapIndex.search(query, k, allowlist) → (scores, chunk_ids). SQL join for metadata enrichment.

4
Delete / compaction

IdMapIndex.remove(chunk_id) is O(1) — no index rebuild. DuckDB compaction protocol unchanged for chunks + files tables. turbovec_indexes BLOB updated post-compaction.

The DbBackend trait interface is unchanged — the TurboVec integration is an implementation detail behind the existing abstraction boundary.

Cargo.toml change (one line) 
[dependencies]
# existing deps unchanged ...
turbovec = "0.x"   # TurboQuant quantization + SIMD search (pure Rust, no system libs)

No new Python dependencies. No new system libraries. TurboVec is a pure Rust crate. Existing duckdb crate dependency retained for metadata storage.

🚀 Delivery Phases

Each phase is independently shippable and reversible. The old float32 path remains live until Phase 4.

Phase 1

Quantized Storage

Add embeddings_quantized table. Write packed codes alongside existing float32 during indexing. Zero user-visible change.

✓ Durable quantized store in place
Phase 2

In-Memory Index

Add turbovec_index.rs module. Load IdMapIndex from quantized table at startup via from_parts(). Persist snapshot to turbovec_indexes.

✓ Fast startup without re-embedding
Phase 3

Search Migration

Expose search_semantic on RustDbWriter PyO3 surface. Route Python search calls to Rust TurboVec. SIMD-accelerated search live.

✓ Full performance gains active
Phase 4

Float32 Removal

Drop embeddings_{dims} float32 tables. Remove DuckDB-VSS extension dependency and the HNSW drop/rebuild lifecycle.

✓ Full memory & disk savings realized

🛡️ Risks & Mitigations

RiskSeverityMitigation
ANN recall loss (0.3% at k=1) Low Use 4-bit (not 2-bit). Recall reaches 1.0 by k=4. ChunkHound returns top 10+ by default — the gap is imperceptible.
TurboVec maturity (v0.x library) Medium Pin to exact version in Cargo.lock. from_parts() is the stable low-level API. Quantization math is well-understood (Lloyd-Max, published at ICLR 2026).
BLOB write amplification at large scale Medium Serialize index only at batch-end, not per-vector. A 1M-vector index at 4-bit/1536-dim ≈ 375 MB — one write per batch is acceptable for a daemon process.
Migration of existing float32 data One-time One-time migration at Phase 4: read float32 from DuckDB → encode via TurboVec → write packed codes. No embedding API calls. Runs as a schema migration step.
Multi-model / multi-dim indexes Handled One IdMapIndex per (provider, model, dims) — same partition pattern as current per-dim tables. Managed in a HashMap in turbovec_index.rs.
Index corruption recovery Handled embeddings_quantized is the durable fallback — always rebuild from packed codes without re-embedding, even if the turbovec_indexes BLOB is corrupt.
