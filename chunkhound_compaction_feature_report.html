ChunkHound — Database Compaction Feature

Feature Design · Architecture · Behaviour Specification
Branch: stack/1-compaction  |  Author: Ariel Vaknin  |  Date: 2026-06-04

📋 Feature Overview

ChunkHound maintains a DuckDB database of parsed code chunks and their vector embeddings. Over time — as files are indexed, re-indexed, and deleted — the database accumulates storage fragmentation that cannot be reclaimed by a simple CHECKPOINT. This compaction feature reclaims that space through a full EXPORT → IMPORT → SWAP rebuild cycle.

🔥 The Problem — Why Compaction is Needed

DuckDB stores data in columnar row groups. When rows are deleted or updated, their storage is not immediately freed — DuckDB marks blocks as free but cannot compact them at CHECKPOINT time. Over a large active codebase this leads to:

  • Growing file size — deleted embeddings keep occupying disk blocks.
  • Query slowdown — HNSW vector scans traverse stale row groups.
  • WAL accumulation — repeated inserts/deletes grow the write-ahead log faster than checkpoints can shrink it.

Fragmentation Sources

SourceTypeCHECKPOINT reclaims?EXPORT/IMPORT reclaims?
Deleted file rowsRow wastePartiallyYes ✓
Re-indexed chunk overwritesRow waste + free blocksNoYes ✓
Free block accumulationBlock-levelNoYes ✓
WAL overheadWAL fileYesYes ✓
HNSW index fragmentationIndex pagesNoYes (rebuild) ✓

Fragmentation Measurement

free_ratio      = free_blocks / total_blocks        # block-level orphan detection
row_waste       = 1 - (live_rows / max_row_id)       # per-table row tombstone ratio
effective_waste = max(free_ratio, row_waste)          # worst-case → threshold gate
Size gate: effective_waste can exceed the threshold while reclaimable bytes are tiny (high-waste ratio on a small DB). A second gate — compaction_min_size_mb — prevents unnecessary cycles when the overhead isn't worth the reclaimed space.

⏸️ Event Deferral Mechanism

During background compaction, the realtime watcher continues receiving filesystem events. Writing to the DB while EXPORT/IMPORT is in progress would race with the SWAP. Events are parked in deferral sets and replayed after SWAP completes.

Deferral Lifecycle

Deferral Sets

SetContentReplay action
_compaction_deferred_filesPaths with pending index operationsRe-index each file
_compaction_deferred_removalsPaths deleted during compaction windowDelete chunks for path
_compaction_deferred_directoriesDirectories deleted during compaction windowDelete all chunks under directory scope
_drained_compaction_removalsShadow set: removals in mid-replay flightCleared on successful reindex
