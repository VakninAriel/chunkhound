Q1
Why is the embedding table named by dimension (embeddings_1536) AND also stores provider, model, and dims per row?
Database Schema Design Answered
Observation: The embedding table is named embeddings_1536 — the dimension is baked into the table name. Yet every single row also stores provider, model, and dims columns. This only makes sense if the table is intended to hold entries from multiple providers and models simultaneously — which feels unusual. A second observation: running ChunkHound with a different embedding model (e.g., 256-dim) causes the code to create a brand new table embeddings_256 rather than adding to the existing one.

Research findings

Root cause: DuckDB's fixed-width typed array constraint

DuckDB declares embedding columns as FLOAT[1536] — a fixed-width typed array. You cannot store a 1024-dim vector in a FLOAT[1536] column. There is no variable-length vector column type. This is why a new table must be created for each distinct dimensionality — it is a hard technical constraint, not a design choice.

-- From duckdb/embedding_repository.py
CREATE TABLE embeddings_{dims} (
    ...
    embedding  FLOAT[{dims}],        -- fixed width: 1536, 1024, 256, etc.
    dims       INTEGER NOT NULL DEFAULT {dims},
    ...
)

Why provider and model columns exist inside the table

Two providers could both produce 1536-dim vectors (e.g., OpenAI text-embedding-3-small = 1536 dims, and hypothetically another provider also at 1536 dims). They would share the same table. The (provider, model) columns distinguish whose embedding is whose.

The unique index enforces one embedding per chunk × provider × model combination — not just per chunk:

CREATE UNIQUE INDEX idx_{dims}_chunk_provider_model_unique
    ON embeddings_{dims}(chunk_id, provider, model);

This means: one chunk can have multiple rows in embeddings_1536 — one per provider/model pair. This enables multi-provider search without separate tables.

Why is dims stored as a column if it's already in the table name?

The dims column is redundant by design — its value always equals the table name suffix. It exists as denormalized metadata for two reasons:

  • Convenience: queries can read dims without parsing the table name string
  • Validation: code can assert row.dims == expected_dims as a sanity check

There is a migration path that enforces uniqueness before adding the constraint, which implies earlier versions lacked the unique index and may have had inconsistent dims values.

Cross-table query behavior

OperationWhich tables?Why
Semantic search One table only — embeddings_{query_dims} Query vector has a fixed dim; only matching table can answer
Existence check (skip re-embed) All tables scanned Need to find if chunk was embedded by any provider/model
Get embedding by chunk id All tables scanned Chunk may be in any dimension table depending on when it was indexed
Summary verdict

The per-dimension table is forced by DuckDB (fixed-width array columns). The provider/model columns inside it exist to handle the edge case where two providers share the same output dimension. The dims column is redundant metadata. The design is technically correct but creates the impression of redundancy — the table name and the column both encode the same number.

Follow-up to explore: In practice, do any two configured providers actually share a dimension (making the per-row provider/model columns load-bearing)? Or is it always one provider per dimension table, making the multi-provider-per-table case theoretical?
Q2
What is the HNSW algorithm and why does ChunkHound use it for vector search?
Database Algorithm Answered
Question: ChunkHound creates an HNSW index on the embedding column with metric = 'cosine'. What is the HNSW algorithm, how does it work, and why is it used here instead of a plain SQL scan?

Explanation

The problem: nearest-neighbor search in high-dimensional space

When you search ChunkHound with a query, that query is turned into a vector (e.g., 1536 numbers). You then need to find the stored chunks whose vectors are most similar to the query vector. The naive approach — compare the query to every single stored vector — is called a brute-force scan. It is O(N × D): every row, every dimension. At 1 million chunks × 1536 dims, that is 1.5 billion float comparisons per query. Too slow.

HNSW solves this with an index structure that reduces query time to approximately O(log N).

Step 1 — Small World graphs

Imagine each vector is a node in a graph. Each node is connected by edges to its K nearest neighbors. To find the nearest neighbor of a query, you start at any entry node and greedily hop to whichever connected neighbor is closest to the query — repeat until no neighbor is closer than the current node. This is called a Navigable Small World (NSW) graph.

The key property: in a well-constructed small world graph, you reach the nearest neighbor in very few hops — similar to the "6 degrees of separation" idea in social networks.

Step 2 — The Hierarchy (the H in HNSW)

NSW alone has a problem: greedy traversal can get stuck in dense local clusters and take many hops. HNSW fixes this by adding multiple layers, like a skip list:

Layer 2 (top):   very few nodes,  very long-range edges  → fast coarse navigation
Layer 1:         more nodes,      medium-range edges
Layer 0 (bottom): ALL nodes,      short-range edges       → precise fine search

Search:  enter at top → greedily descend layer by layer → bottom layer gives final result

The higher layers let the search "teleport" across the space quickly. Lower layers refine the result locally. This is why query time is O(log N) — the hierarchy prunes the search space exponentially at each level.

Cosine similarity — what metric ChunkHound uses

The index is built with metric = 'cosine'. Cosine similarity measures the angle between two vectors, not their distance:

cosine_similarity(A, B) = (A · B) / (|A| × |B|)
-- Result: 1.0 = identical direction (most similar)
--         0.0 = perpendicular (unrelated)
--        -1.0 = opposite directions

-- DuckDB's array_distance() returns 1 - similarity (lower = closer):
ORDER BY array_distance(e.embedding, query_vector)  -- ascending = most similar first

Cosine is preferred over Euclidean distance for semantic embeddings because it captures meaning direction regardless of vector magnitude. Two chunks about the same concept will point in the same direction even if their vectors have different lengths.

Approximate — the tradeoff

HNSW is an Approximate Nearest Neighbor (ANN) algorithm. It does not guarantee finding the single mathematically closest vector every time. In exchange it is orders of magnitude faster. In practice, recall is typically 95–99%+ — the few missed results are very close in similarity to the true nearest neighbor and would not meaningfully change the search output.

MethodQuery timeAccuracyMemory
Brute-force scanO(N × D)100% exactO(N × D)
HNSWO(log N)~95–99%O(N × M) — M = edges/node

Why ChunkHound drops and recreates the HNSW index during bulk inserts

Building the HNSW graph requires connecting each new node to its neighbors — an expensive operation per insert. When inserting more than ~50 embeddings at once, ChunkHound drops the index, bulk-inserts all rows, then rebuilds the index in one pass. Rebuilding from scratch once is 10–20× faster than incrementally adding 1000 nodes one by one.

-- Before bulk insert
DROP INDEX IF EXISTS idx_hnsw_1536;

-- ... INSERT 1000 rows ...

-- After bulk insert — rebuild in one pass
CREATE INDEX idx_hnsw_1536
    ON embeddings_1536 USING HNSW (embedding)
    WITH (metric = 'cosine');
One-line summary

HNSW is a multi-layer graph index that lets ChunkHound find semantically similar code chunks in O(log N) time instead of scanning every row. It trades a small amount of recall accuracy (~1–5%) for query speeds that scale to millions of chunks. The cosine metric means "most similar meaning," not "closest in Euclidean space."

Q3
What is LIKE in a SQL query?
Database SQL Basics Answered
Question: The ChunkHound regex/text search uses LIKE in its SQL queries. What does LIKE do, and how is it different from semantic (vector) search?

Explanation

What LIKE does

LIKE is a SQL pattern-matching operator. It checks whether a text column matches a pattern string. Two wildcard characters control the match:

WildcardMeaningExample
%Zero or more of any character'%search%' matches anything containing "search"
_Exactly one of any character'get_' matches "get_" followed by any single char
-- Find all chunks whose code contains the word "search"
SELECT * FROM chunks WHERE code LIKE '%search%';

-- Find all chunks whose symbol starts with "get_"
SELECT * FROM chunks WHERE symbol LIKE 'get_%';

-- Find file paths ending in .py
SELECT * FROM files WHERE path LIKE '%.py';

How ChunkHound uses it

The regex search mode in ChunkHound wraps your query in %…% and runs a LIKE scan on the chunks.code column — essentially "find all chunks whose source text contains this string":

-- ChunkHound regex search (simplified)
SELECT c.id, c.symbol, c.code, c.start_line, f.path
FROM chunks c
JOIN files f ON c.file_id = f.id
WHERE c.code LIKE '%def search%'   -- user typed: def search
  AND f.path LIKE '%services%'     -- optional path filter
ORDER BY f.path, c.start_line
LIMIT 50;

LIKE vs. semantic (vector) search — the key difference

LIKEVector / HNSW
MatchesExact characters in the textMeaning / concept
Example query%IndexingCoordinator%"how does indexing work"
MissesSynonyms, different spelling, paraphrasesExact symbol names
Needs embeddings?No — works offlineYes — requires API call
SpeedSequential table scan — O(N)HNSW graph — O(log N)
Use whenYou know the exact name/stringYou know the concept, not the name

Important: LIKE is case-sensitive in DuckDB

In DuckDB (and most SQL databases), LIKE is case-sensitive by default. '%Search%' will not match "def search". To match case-insensitively use ILIKE:

WHERE code ILIKE '%search%'   -- matches Search, SEARCH, search, etc.
One-line summary

LIKE is SQL's text pattern matcher — % is a wildcard for "anything". It does a literal string search through every row (no index), which is why it's used for ChunkHound's offline/regex mode and semantic vector search is preferred for large codebases.

Q4
What is the CAST algorithm and how does ChunkHound use it?
Algorithm Parsing Answered
Question: The learning guide mentions "CAST algorithm" in the parsers section. What does it stand for, what problem does it solve, and how does it work step by step?

Explanation

What CAST stands for

cAST = Code Abstract Syntax Tree. It is named after a research paper: "cAST: Enhancing Code Retrieval-Augmented Generation with Structural Chunking via Abstract Syntax Tree". ChunkHound implements a simplified, production-adapted version of that paper's ideas.

The core problem it solves: how do you split a source file into chunks that are useful for vector search? If you split naively by line count or character count, you break functions in half and destroy semantic meaning. CAST splits along the natural boundaries of the code's syntax tree instead.

The pipeline: from file to Chunk objects

Source file (.py, .ts, .go …)
    │
    ▼ tree-sitter
AST (Abstract Syntax Tree) — language-specific parse tree
    │
    ▼ ConceptExtractor  (universal_engine.py)
UniversalChunk list  — language-agnostic semantic units
    │
    ▼ cAST algorithm  (chunk_splitter.py + universal_parser.py)
Optimised UniversalChunk list  — right-sized, non-overlapping
    │
    ▼ universal_to_chunk()
Chunk objects  — stored in DB, embedded, searched

Tree-sitter builds the parse tree. The CAST algorithm then decides how to group and size the semantic nodes into chunks that fit the embedding model's token limit.

Key size parameters (CASTConfig)

@dataclass
class CASTConfig:
    max_chunk_size:   int   = 1200   # non-whitespace chars — primary size limit
    min_chunk_size:   int   = 50     # avoid tiny fragments
    merge_threshold:  float = 0.8    # merge siblings if combined < 80% of max
    greedy_merge:     bool  = True   # merge adjacent sibling nodes
    safe_token_limit: int   = 6000   # safety cap for embedding model

Size is measured in non-whitespace characters (spaces/tabs/newlines stripped out) — not raw characters, not lines. This is what "codepoint-aware" means: the metric fairly represents actual content regardless of indentation style.

The 5-phase algorithm

#PhaseWhat happens
1 Deduplication Remove any UniversalChunks with identical content before processing
2 Concept grouping Group chunks by semantic type: DEFINITION (functions/classes), BLOCK (code blocks), COMMENT
3 Concept-specific strategy DEFINITION chunks stay whole; BLOCK chunks merge aggressively; COMMENT chunks merge only if adjacent
4 Recursive splitting Any chunk still over max_chunk_size (1200 chars) or safe_token_limit (6000 tokens) is split by lines, or by emergency byte-split for minified code
5 Greedy merge pass Final pass: adjacent compatible chunks are merged if the combined result still fits — maximises information density per chunk

How nesting is handled (class + methods)

The merge pass explicitly detects when one chunk is nested inside another (its line range is fully contained) and refuses to merge them. A class body and its methods stay as separate chunks:

-- Example: MyClass spans lines 10-50
-- method1() spans lines 15-20  →  nested, NOT merged into class chunk

is_nested = (
    next_chunk.start_line > current_chunk.start_line
    and next_chunk.end_line <= current_chunk.end_line
)
if is_nested:
    keep_separate()   # methods stay independent — searchable on their own

This is important for search quality: a query about a specific method finds that method's chunk, not the entire class file.

Why this matters for vector search

The quality of semantic search depends directly on chunk quality. If a chunk contains one tiny 3-line helper and a completely unrelated 50-line function, the embedding will be a confused average of both — searches for either concept will score lower. CAST's goals:

  • Preserve syntactic integrity — never cut a function in the middle
  • Maximise information density — fill each chunk to ~1200 chars so embeddings are rich
  • Language invariance — same algorithm works for Python, TypeScript, Go, etc. because tree-sitter normalises the AST
  • Fit token limits — embedding APIs refuse inputs over ~8192 tokens; 6000 is the safe cap
One-line summary

CAST uses tree-sitter's parse tree to split code at natural semantic boundaries (function end, class end), then greedily merges small adjacent chunks to maximize embedding richness, never crossing the embedding model's token limit. The result is chunks that are both semantically coherent and right-sized for vector search.

Q5
What is multi-hop search and how does ChunkHound implement it?
Algorithm Search Answered
Question: The learning guide mentions "multi-hop search" and "single-hop search" as two different search strategies. What does "hop" mean here, how does multi-hop differ from single-hop, and when is each used?

Explanation

The core idea

A single-hop search does exactly one thing: embed the query → run HNSW vector search → return top-K results. Fast, simple, one round trip.

A multi-hop search treats those initial results as a starting point and then expands outward — finding neighbors of the top results, reranking everything together, then expanding again — until the results stop improving. Each expansion round is a "hop."

The analogy: single-hop is looking up one page in a book. Multi-hop is reading that page, then following the footnotes, then following those footnotes, stopping when you're no longer finding anything new.

Single-hop flow (always available)

Query string
  │
  ▼ embed (1 API call)
Query vector
  │
  ▼ HNSW cosine search (1 DB query)
Top-K chunks ranked by vector similarity
  │
  ▼ return

Cost: 1 embedding call + 1 DB query. Used when the provider does not support reranking (e.g. OpenAI embeddings only).

Multi-hop flow (requires reranking provider — e.g. VoyageAI)

Query string
  │
  ▼ 1. Initial search — HNSW returns ~300 candidates
  │
  ▼ 2. Rerank all 300 via VoyageAI rerank-2
  │       scores updated — top-5 identified
  │
  ▼ 3. Expand — find 20 vector-neighbors of each top-5 chunk
  │       ~100 new candidates added to the pool
  │
  ▼ 4. Rerank entire pool (300 + 100 = 400 docs) — scores updated again
  │
  ▼ 5. Check termination — if still improving, go to step 3 with new top-5
  │
  ▼ 6. When terminated — paginate final ranked pool, return top-K

Each iteration of steps 3–5 is one "hop." The pool grows, gets reranked, and either expands again or stops.

What reranking adds (and why it matters)

HNSW finds chunks that are close in vector space. That is a proxy for relevance — good, but imperfect. A reranker (VoyageAI rerank-2) is a separate model trained specifically to score document–query relevance. It sees both the query text and the chunk text together and outputs a richer relevance score.

Result: chunks that were ranked #8 by HNSW similarity might jump to #1 after reranking because the reranker understands the query intent better. Multi-hop iteratively applies this to an expanding pool, so progressively better candidates surface.

The 5 termination conditions

#ConditionDefault threshold
1Time limit exceeded5 seconds (normal) / 600s (exhaustive mode)
2Result cap reached500 chunks accumulated
3Not enough quality candidates to expand fromNeed 5+ chunks with score > 0.0
4Score degradation — a top chunk's score droppedDrop ≥ 0.15 from previous round
5Minimum relevance too lowTop-5 minimum score < 0.3

Conditions 4 and 5 detect "diminishing returns" — the expansion is no longer surfacing better results, so it's not worth continuing.

Strategy selection — automatic

-- search_service.py auto-selects based on provider capability:

if provider.supports_reranking():
    use MultiHopStrategy    # VoyageAI → multi-hop
else:
    use SingleHopStrategy   # OpenAI embeddings only → single-hop

-- Can be overridden:
force_strategy = "multi_hop"   # force multi-hop
force_strategy = "single_hop"  # force single-hop

Single-hop vs multi-hop at a glance

Single-hopMulti-hop
API calls1 embed1 embed + 1–5 rerank calls (100–500 docs each)
DB queries1 HNSW search1 HNSW + N neighbor lookups per round
Latency~100ms1–5 seconds
Best forSimple lookups, known symbol namesComplex questions, exploring a concept across files
RequiresAny embedding providerProvider with reranking (VoyageAI)
Result qualityGoodBetter — reranker understands query intent

ContextRetriever — the companion utility

Not part of the hop loop itself, but used alongside it. Given a chunk_id, it fetches the surrounding chunks (the N lines before and after) from the same file. This gives the caller a window of code context around each result — useful when the AI assistant needs to understand what comes before/after a match.

-- Overlap query: find all chunks that touch lines (start-5) to (end+5)
SELECT symbol, start_line, end_line, code, chunk_type
FROM chunks
WHERE file_id = ?
  AND (start_line BETWEEN ? AND ? OR end_line BETWEEN ? AND ?
       OR start_line <= ? AND end_line >= ?)
ORDER BY start_line;
One-line summary

Multi-hop search starts with a normal HNSW vector search, then iteratively finds neighbors of the best results and reranks the growing pool — stopping when relevance stops improving. It trades latency (1–5 seconds vs ~100ms) for significantly better result quality on complex queries, and only activates when the embedding provider supports reranking.

Q6
Multi-hop reranking: why rerank at all if we have cosine similarity, and why re-score the original 300 in round 2?
Algorithm Search Answered
Two questions:
  1. We already have cosine similarity scores from HNSW. Why do we need to rerank the initial 300 results at all?
  2. In round 2 we expand to 400 chunks (300 original + 100 new). Why do we rerank all 400 instead of just scoring the 100 new ones?

Question 1 — Cosine similarity vs reranking: two different signals

What cosine similarity actually measures

When HNSW returns the top-300, each chunk's score is the cosine similarity between the query embedding and the chunk embedding. Both were embedded independently — the query was embedded alone, then compared to chunk vectors that were embedded weeks ago during indexing. The similarity is inferred from their positions in the same vector space.

This is an indirect proxy for relevance. It answers: "do these two vectors point in a similar direction?" — not "does this chunk actually answer the question?"

What a reranker measures

A reranker (VoyageAI rerank-2) is a cross-encoder model. It receives the query text and a chunk's text together in one input and produces a relevance score for that specific pair. It can read both simultaneously and reason about their relationship.

-- Cosine (bi-encoder): embed separately, compare vectors
embed("how does JWT refresh work?")   →  vector A
embed("def refresh_token(...)  ...")  →  vector B
score = cosine(A, B)                  →  0.72   (geometric angle)

-- Reranker (cross-encoder): see both at once
rerank(
    query="how does JWT refresh work?",
    doc="def refresh_token(...): ..."
)  →  0.91   (semantic relevance judgment)

The reranker can catch things cosine misses:

  • Query uses different terminology than the code — cosine may score low; reranker understands the concept
  • A chunk is about the right topic but doesn't answer the query — cosine scores it high; reranker scores it low
  • A chunk answers the query indirectly — cosine may miss it; reranker recognises the relevance

Analogy

Cosine similarity is like matching book covers — fast, works at scale, but imprecise. Reranking is like actually reading the relevant pages — slower, but accurate. HNSW narrows 1M chunks to 300 candidates (cover matching). The reranker then reads all 300 to find the true top-10 (reading the pages). Doing a full read on 1M chunks would be too expensive; doing cover-matching on 300 is wasteful when you can afford to read them.

Summary answer to Q1

Cosine similarity is a fast filter — it gets you in the right neighbourhood. Reranking is a precision model — it finds the right house in that neighbourhood. You need both because cosine alone cannot model query–document relevance at a semantic level; it only measures geometric proximity in embedding space.

Question 2 — Why re-score the original 300 in round 2?

Reranking is not additive — it scores a batch, not individual documents

When you call rerank(query, documents=[...300 docs...]), the reranker produces scores across the whole batch. In round 2 you have 400 documents. The problem with not re-scoring the original 300 is that the two sets of scores are on incompatible scales:

  • Round 1 scores: the reranker calibrated across 300 documents
  • The 100 new chunks: they only have raw cosine scores from HNSW neighbor lookup

You cannot simply compare a round-1 rerank score of 0.85 against a cosine score of 0.72 — they come from completely different models with different scales. Merging them would produce nonsense rankings.

The competition analogy

Imagine a 300-runner race. You rank them: #1 = Alice, #2 = Bob … then 100 new runners arrive. You cannot say "I already know Alice is #1, so just race the 100 newcomers against each other and slot them in." The new runners might be faster than Alice. You have to run the full race with all 400 to get a fair unified ranking.

Reranking the original 300 again in round 2 is exactly that: running the full race again with all 400 participants to get honest, comparable scores across the entire pool.

The secondary benefit: score drift detection

Re-scoring the original 300 also serves the termination logic. The algorithm tracks whether the top-5 chunks' scores drop after expansion (termination condition 4: drop ≥ 0.15). If the new 100 chunks are better than some of the original top-5, their scores will drop in the new ranking — signalling that the search space is saturated and further expansion won't help. This only works if all 400 are scored on the same scale in the same call.

-- Round 1: [A=0.91, B=0.88, C=0.85, D=0.80, E=0.75, ...]  ← top-5 tracked
-- Round 2: rerank all 400 → [X=0.93, A=0.89, Y=0.87, B=0.72, C=0.70, ...]
--           B dropped 0.88 → 0.72 = drop of 0.16 ≥ 0.15 → TERMINATE
One-line answers

Q1: Cosine similarity measures geometric closeness of independently-created vectors; a reranker measures actual query–document relevance by reading both together — a fundamentally better signal that cosine cannot replicate.

Q2: Scores from different rerank batches are on incompatible scales; you must score all candidates in one call to get a unified, comparable ranking — and re-scoring the originals also enables the score-drop termination check.

Q7
Is there a benefit to deduplicating before reranking all 400 vectors?
Algorithm Search Answered
Question: In multi-hop round 2 we rerank all 400 documents (300 original + 100 new). Would it be beneficial to deduplicate near-identical chunks before sending them to the reranker?

What ChunkHound already does

Exact dedup by chunk_id — already implemented

ChunkHound already deduplicates using a seen_chunk_ids set. When expanding, any neighbor whose chunk_id is already in the pool is silently dropped:

# multi_hop_strategy.py lines 163, 217-219
seen_chunk_ids = {result["chunk_id"] for result in initial_results}
...
if neighbor["chunk_id"] not in seen_chunk_ids:
    new_candidates.append(neighbor)
    seen_chunk_ids.add(neighbor["chunk_id"])

So the same chunk will never appear twice in the 400. What ChunkHound does not do is detect two different chunks with nearly identical content.

The question is about semantic / content-level dedup

When near-duplicate chunks exist in practice

Even with unique chunk IDs, a codebase can produce near-duplicate content chunks:

  • Copy-pasted helper functions across files
  • Overloaded methods with identical bodies
  • Generated boilerplate (e.g., 10 identical __init__ methods)
  • A function and its test mock that mirror each other

In such cases the 400-document pool might contain 30 near-identical chunks, all of which will receive similar rerank scores — crowding out diverse results.

Benefits of content-level dedup before reranking

BenefitHow much it matters
API cost reduction — reranking charges per document/token. Fewer docs = cheaper call. Meaningful if the codebase has lots of repeated patterns. Minor otherwise.
Result diversity — final top-K won't be filled with 8 variations of the same function. High value for user experience — 10 diverse results > 10 near-identical ones.
Reranker score distribution — near-duplicates cluster at similar scores and dilute the top-K slots, pushing genuinely different relevant chunks off the page. Moderate — depends on how many duplicates exist.

Costs and complications

CostReality
You already have the embeddings — so dedup is cheap: compute cosine between all 400 pairs to find near-duplicates. 400 × 400 = 160,000 comparisons at 1536 dims each. Fast in-memory but non-trivial.
Threshold choice — what cosine similarity defines "duplicate"? 0.98? 0.95? Requires tuning. Too aggressive = drop legitimate results. Too loose = no effect.
Information loss — two nearly-identical chunks from different files might both be relevant (same pattern used in two contexts). Real risk. A user might want to know the pattern appears in multiple places.
Termination logic breaks — the score-drop detection tracks specific chunk_ids across rounds. If you dedup and drop a tracked chunk, the termination signal misfires. Fixable but adds complexity.

Better alternative: dedup at result display time, not before reranking

Rather than deduplicating the rerank input (which distorts the scoring), a cleaner approach is to dedup the final output:

  1. Rerank all 400 normally — get clean, comparable scores
  2. Walk the ranked list top-to-bottom
  3. For each result, check if a near-identical chunk is already in the output set
  4. If yes, skip it (but keep a reference like "also found in file X")
  5. Return top-K diverse results

This preserves reranking integrity (all 400 scored fairly) and still gives the user diverse results. The cost is tiny — you're only comparing against the already-accepted top-K, not all 400 pairs.

ChunkHound's current state: Does not implement content-level dedup at either stage. The exact chunk_id dedup prevents the same chunk appearing twice, but near-duplicate content from different chunks will both reach the reranker and both appear in results. This is a real gap for codebases with a lot of repeated patterns.
Answer

Yes, content-level dedup has real benefits — mainly result diversity and cost. But doing it before reranking risks distorting scores and breaking termination logic. The right place to dedup is after reranking, before returning results — where you already have reliable scores and can collapse near-duplicates without affecting the ranking math. ChunkHound does not currently do this.

Q8
What exactly happens in the "expand" stage of multi-hop search?
Algorithm Search Answered
Question: Multi-hop search "expands" from the top-5 results to find more candidates. What does "expand" mean mechanically — does it follow code references, traverse a graph, or something else?

The short answer

Expand = run a new HNSW search using a found chunk's embedding as the query vector

There is no graph traversal, no code reference following, no AST relationship tracking. "Expand" means: take one of the top-5 chunks from the current round, look up its stored embedding vector, and use that vector as the input to a brand new HNSW nearest-neighbor search. The result is the 20 chunks that live closest to it in embedding space.

-- Expand around candidate chunk #42:

-- Step 1: fetch chunk #42's embedding vector
SELECT embedding FROM embeddings_1536
WHERE chunk_id = 42 AND provider = 'voyageai' AND model = 'voyage-3';
-- returns: [0.012, -0.834, 0.441, ...]   ← 1536 floats

-- Step 2: use that vector as a new HNSW query
SELECT
    c.id AS chunk_id, c.symbol, c.code, c.start_line, c.end_line,
    f.path AS file_path,
    1.0 - array_cosine_distance(e.embedding, [0.012,-0.834,0.441,...]::FLOAT[1536]) AS score
FROM embeddings_1536 e
JOIN chunks c ON e.chunk_id = c.id
JOIN files f  ON c.file_id  = f.id
WHERE e.provider = 'voyageai'
  AND e.model    = 'voyage-3'
  AND c.id != 42          -- exclude the seed chunk itself
ORDER BY array_cosine_distance(e.embedding, [...]) ASC
LIMIT 20;                 -- 20 neighbors in normal mode, 30 in exhaustive

Why this is more powerful than just asking HNSW for 300 results instead of 100

This is the key insight. The original HNSW search uses the query embedding — a vector encoding what the user asked. The expansion uses a result chunk's embedding — a vector encoding what a good answer looks like.

These two vectors point to different places in embedding space:

Query: "how does JWT token refresh work?"
→ query embedding lives near: authentication, tokens, sessions, expiry concepts

Top result chunk: def refresh_token(user_id, old_token): ...
→ chunk embedding lives near: token rotation, revocation, database writes, audit logs

Expanding from the chunk finds: token_store.invalidate(), audit_log.record(),
session_cleanup(), rotation_policy — code that looks like the ANSWER,
not code that looks like the QUESTION.

Simply increasing HNSW's initial LIMIT from 100 to 400 would return more chunks that look like the question — all clustered around authentication concepts. Expansion from a found answer reaches different corners of the embedding space that the query vector never pointed at.

The expand loop step by step

StepWhat happensNumbers (normal mode)
1. Select seeds Take top-5 chunks from the current reranked pool 5 chunks
2. Fetch each seed's embedding SELECT embedding FROM embeddings_{dims} WHERE chunk_id = ? 5 DB reads
3. Run HNSW per seed Each seed embedding becomes a new query vector 5 HNSW searches
4. Filter already-seen Drop any neighbor chunk_id already in seen_chunk_ids set up to 100 new chunks
5. Add to pool Append new chunks to all_results pool grows: 300 → up to 400
6. Rerank entire pool Send all docs to reranker, update scores 1 rerank API call on ~400 docs
7. Check termination Score drop? Time limit? Quality too low? If no → go back to step 1 with new top-5

What "neighbors in embedding space" means conceptually

Two chunks are neighbors if their vectors have high cosine similarity — meaning the embedding model assigned them similar positions in the 1536-dimensional space because they discuss similar concepts. This is not based on:

  • File proximity (they can be in completely different files)
  • Code references (no import/call-graph analysis)
  • Lexical similarity (they don't need shared keywords)

It is purely: "the embedding model thinks these chunks are about the same thing." Two chunks from completely unrelated files that both handle token expiry will be neighbors even if they never reference each other.

How many hops typically happen in practice?

The 5-second time limit (normal mode) usually allows 2–4 expansion rounds before termination — partly from time, partly from the score-drop or minimum-relevance conditions. In exhaustive mode (600s timeout) the loop can run many more rounds, but typically converges in 5–10 because the score-drop condition fires once the neighborhood is saturated.

Mental model: Think of the embedding space as a city map. The query vector is your starting address. HNSW finds the 300 buildings closest to that address. Expansion says: "the best building we found is on Oak Street — now find the 20 buildings closest to Oak Street, not to where we started." Each hop explores a new neighbourhood centred on a good answer, not on the original question.
One-line summary

Expand = look up a good result's stored embedding vector, run a fresh HNSW search using it as the query, collect the 20 nearest chunks (that haven't been seen yet), and add them to the pool. No graph traversal — purely re-using HNSW with answer-vectors instead of the original question-vector.

Q9
Does reranking happen only at the end on all 400 docs, or also during intermediate expansion steps?
Algorithm Search Answered
Question: We know reranking runs on the accumulated pool of ~400 docs. Does it also run during intermediate expansion steps, or only once at the end?

Answer: reranking runs after EVERY expansion round — not just at the end

The full reranking timeline

Round 0 (initial):
  HNSW → 300 candidates
  RERANK all 300  ← rerank #1
  → top-5 identified → used as seeds for expansion

Round 1 (first expand):
  find 20 neighbors × 5 seeds = up to 100 new chunks
  pool grows 300 → up to 400
  RERANK all 400  ← rerank #2
  → new top-5 identified → seeds for next expansion

Round 2 (second expand):
  find 20 neighbors × 5 new seeds = up to 100 more new chunks
  pool grows 400 → up to 500
  RERANK all 500  ← rerank #3
  → check termination conditions
  → if not done, repeat...

Final output:
  apply threshold filter
  paginate top-K from the last reranked pool

There is no separate "final rerank." The last rerank that ran is the final ranking. The pool is always fully reranked before the next expansion decision is made.

From the actual code — two rerank call sites

-- Call site 1: after initial HNSW search (line 133)
rerank_results = await self._embedding_provider.rerank(
    query=query,
    documents=documents,          -- the initial 300
    top_k=len(documents),
)

-- Call site 2: inside the expansion loop, after each expand (line 246)
rerank_results = await self._embedding_provider.rerank(
    query=query,
    documents=[result["content"] for result in all_results],  -- growing pool
    top_k=len(documents),
)

Both calls have identical structure. The only difference is that the second call is inside the while True loop — it runs once per expansion round.

Why reranking must happen at every intermediate step — not just at the end

The rerank scores after each round are what drive the next expansion. The algorithm picks the top-5 seeds for the next hop based on the current rerank scores:

top_candidates = [r for r in all_results if r.get("score", 0.0) > 0.0][:5]

If you skipped intermediate reranks and only reranked at the very end, you would have to choose the next seeds using raw cosine scores — which are the weaker signal. The expansion would be guided by the wrong metric, finding neighbors of chunks that are geometrically close to the query but not actually the most relevant. The whole point of multi-hop is that each hop is guided by reranker judgment, not cosine judgment.

The termination conditions also depend on intermediate rerank scores

Two of the five termination conditions read from rerank scores that are updated every round:

  • Score degradation — tracked chunks' scores are compared round-over-round. This only works if reranking runs every round.
  • Minimum relevance — the top-5 minimum score is checked after each rerank. Without intermediate reranks, you'd have no signal to stop early.

If reranking only happened once at the end, the algorithm would have to run until the time limit or result cap — it could never stop early because it would have no score signal to check.

Cost implication

This means the reranking API is called once per expansion round, each time on a growing document pool. If multi-hop runs 3 rounds:

RoundDocs rerankedAPI call
Initial~300rerank #1
Expansion 1~400rerank #2
Expansion 2~500rerank #3
Total~1200 doc-scorings3 API calls

The growing pool size also explains why the 5-second time limit exists — each rerank call on 500 docs takes real time, and the loop compounds it.

One-line summary

Reranking runs after every single expansion round — not just at the end. The rerank scores from each round are the steering wheel for the next hop: they decide which 5 chunks become the expansion seeds. Without intermediate reranks, multi-hop would have no way to guide itself or terminate early.

Q10
Does reranking happen after each of the 5 individual HNSW queries during expansion, or once after all 5 complete?
Algorithm Search Answered
Observation: During the expand stage we noticed what looked like rerank calls happening, possibly one after each of the 5 HNSW vector queries. Is there 1 rerank per expansion round, or 5?

Answer: 1 rerank per expansion round — not 5

The exact code (multi_hop_strategy.py lines 196–250)

-- EXPANSION LOOP for one round:

new_candidates = []
for candidate in top_candidates:           # ← iterates 5 times
    neighbors = self._db.find_similar_chunks(
        chunk_id=candidate["chunk_id"], ... # ← HNSW vector query #1, #2, #3, #4, #5
    )
    for neighbor in neighbors:             # ← collect results, no rerank here
        if neighbor["chunk_id"] not in seen_chunk_ids:
            new_candidates.append(neighbor)
            seen_chunk_ids.add(neighbor["chunk_id"])

# ← for loop is DONE — all 5 HNSW queries complete

all_results.extend(new_candidates)         # ← add ALL new chunks at once

rerank_results = await self._embedding_provider.rerank(  # ← ONE rerank call
    query=query,
    documents=[result["content"] for result in all_results],
    top_k=len(documents),
)

The rerank call is outside the for loop. The 5 HNSW queries run to completion first, all their results are collected into new_candidates, added to all_results, and only then is a single rerank call made on the entire accumulated pool.

So for 3 expansion rounds: 15 HNSW DB queries (5 per round) and 4 rerank API calls (1 initial + 1 per round). The two operations are completely separate and do not interleave.

Why the observation of "5 rerank calls" was misleading

What you likely saw was the 5 find_similar_chunks DB calls — one per top-5 seed chunk, each running a full HNSW vector search. These are database queries, not rerank API calls. They look similar in a trace because both are async operations that resolve one after another during the expansion phase. The single rerank then fires after all 5 DB queries complete.

Q11
What does unified_search.py do, and does it reconcile with the multi-hop explanation?
Algorithm Search Answered
Question: chunkhound/services/research/shared/unified_search.py has its own search flow. Does it contradict or extend what we described for multi-hop search?

Short answer: it reconciles — it is a higher layer that wraps multi-hop

Where it sits in the system

Everything discussed in Q5–Q10 about multi-hop search describes MultiHopStrategy — the vector-search engine. UnifiedSearch is a research-mode orchestrator that calls multi-hop as its first step, then adds a symbol-extraction + regex layer on top. It is only used in the research command, not in the regular search command.

chunkhound search "..."   →  MultiHopStrategy (or SingleHopStrategy) directly

chunkhound research "..."  →  UnifiedSearch (7-step pipeline)
                                   └── step 2: calls MultiHopStrategy internally

The 7-step UnifiedSearch pipeline

StepWhat happensOutput
1 Multi-hop semantic search (force_strategy="multi_hop") — the entire flow from Q5–Q10 happens here, including all internal expansion rounds and reranks ~30–500 semantically ranked chunks
2 Extract symbols from semantic results — reads chunk.symbol, parameter names, and parameter types already stored by the CAST parser. No re-parsing. Ordered list of symbol names (e.g. refresh_token, TokenStore)
3 Select top-N symbols (default: config.max_symbols). Preserves first-seen order from ranked semantic results. Trimmed symbol list
4 Parallel regex search for each symbol — runs LIKE pattern searches concurrently across the DB, paginating until target-per-symbol found. Excludes chunk IDs already in semantic results. Additional chunks not found by vector search
5 Unify: merge semantic + regex results deduplicating by chunk_id. Semantic results take priority. Combined pool
6 Final unified rerank — reranks the entire combined pool against the ROOT query (not the BFS sub-query). If compound reranking: runs one rerank per query, averages scores. Final ranked list

The key insight: vector search misses exact symbol references

Multi-hop finds chunks that are semantically similar to the query. But consider: you search for "how does token refresh work?" — multi-hop finds the refresh_token() function. However, there may be a completely different file (audit_logger.py) that calls refresh_token() by exact name but is not semantically about token refresh. Its embedding vector might not be close to the query vector at all.

Symbol extraction + regex finds this: it reads the symbol name refresh_token from the semantic results and then searches the whole codebase for any chunk whose code contains \brefresh_token\b. This catches callers, tests, wrappers — code that uses the relevant symbol but doesn't discuss it semantically.

Why the final rerank uses the ROOT query, not the sub-query

In research mode, ChunkHound explores a topic via BFS — breaking the question into sub-queries at each depth level. Each call to UnifiedSearch might be for a sub-query like "JWT revocation list implementation." The final Step 6 rerank deliberately uses the original root question ("how does authentication work?") — not the sub-query. The comment explains:

# Step 7: Unified rerank against ROOT query (not BFS queries)
# Prevents diversity collapse — a sub-query rerank would score everything
# "about JWT revocation" highly, pushing out other relevant chunks.
# Root query reranking keeps the final ranking aligned with the user's
# original intent.

Total rerank calls in a full UnifiedSearch run

StageRerank callsDocuments per call
Multi-hop initial1~100
Multi-hop expansion (per round)1 per round (~2–4)~200–500 growing
UnifiedSearch Step 6 (final unified)1 (or N for compound)semantic + regex combined

This explains what was observed earlier — multiple rerank calls happen during a research query: most are the internal multi-hop expansion reranks, plus one final unified rerank at the end.

Stack summary:
research command
  └── UnifiedSearch.unified_search() — 7-step pipeline
      └── step 1: SearchService.search_semantic(force_strategy="multi_hop")
          └── MultiHopStrategy.search() — HNSW + iterative expand + rerank per round
      └── steps 2–5: symbol extraction + parallel regex
      └── step 6: final unified rerank against root query
Reconciliation

Everything said about multi-hop in Q5–Q10 is correct — it describes the inner engine. UnifiedSearch is a research-mode wrapper that calls that engine, then adds a second search dimension (symbol-based regex) to find chunks that reference relevant code by name rather than by meaning, and finishes with one more rerank that unifies both dimensions against the user's original question.

Q12
Is unified_search() called multiple times per research query, and why?
Algorithm Research Answered
Question: UnifiedSearch.unified_search() is called from the research BFS engine. Is it called once per research query, or multiple times? Why?

Answer: yes — once per BFS node, up to 4 times total

The full research pipeline (BFS with depth=1)

User: chunkhound research "how does authentication work?"

Step A — Initial search (call #1)
  deep_research() calls unified_search(root_query)
  → returns initial chunks
  → root BFS node populated

Step B — LLM generates follow-up questions (no search)
  QuestionGenerator sees the initial chunks
  LLM asks: "what unexplored code elements did I see?"
  → generates up to 3 sub-questions:
      "how does JWT token refresh work?"
      "where is the session store implemented?"
      "how does the logout flow invalidate tokens?"

Step C — BFS depth 1: one unified_search() per follow-up (calls #2, #3, #4)
  _process_node("how does JWT token refresh work?")   → unified_search() call #2
  _process_node("where is session store implemented?") → unified_search() call #3
  _process_node("how does logout invalidate tokens?")  → unified_search() call #4
  (all 3 run concurrently)

  Each call:
    - runs multi-hop search for its sub-question
    - extracts symbols, runs regex
    - checks: did we find NEW chunks not seen yet?
    - if 0 new chunks → marks as terminated leaf, no further children

Step D — No depth 2 (MAX_DEPTH = 1)
  Even if follow-up nodes found new info, they generate no children.
  BFS stops.

Why BFS at all — why not just search the root query harder?

A single multi-hop search on "how does authentication work?" starts from the query vector and expands outward in embedding space. It finds chunks that are semantically similar to authentication. But it will miss code that is topically adjacent but not semantically close — e.g., rate limiting, CSRF protection, or audit logging — because those concepts don't appear in the original query vector's neighborhood.

The BFS approach lets an LLM look at what was found and generate targeted follow-up questions about the gaps it observes. Each follow-up query creates a new vector neighborhood to explore. This covers the topic from multiple angles rather than one expanding sphere.

Query expansion: each unified_search() call is actually 3 searches in parallel

Before calling unified_search(), PluggableResearchService expands each query into 3 variants using an LLM — the original + 2 rephrasings. All 3 are searched in parallel inside unified_search() and deduplicated by chunk_id. This means one BFS node = 3 parallel multi-hop searches.

unified_search("how does JWT token refresh work?")
  └─ parallel semantic search × 3 queries:
       "how does JWT token refresh work?"          (original)
       "token rotation and refresh implementation" (LLM variant 1)
       "refresh token validation and storage"      (LLM variant 2)
  └─ deduplicate results
  └─ symbol extraction + regex
  └─ final unified rerank against ROOT query

Early termination — why you often see fewer than 4 calls

Before each follow-up search runs, the BFS checks: does this sub-query's query vector overlap significantly with chunks already explored? If a node's search returns zero new chunks (all results were already in global_explored_data), it's marked a terminated leaf and generates no further children. In practice, the third follow-up often terminates early for queries about well-contained topics.

Full architecture stack for one research query:

                  └── symbol extraction + regex

One-line summary

unified_search() is called once for the initial query plus once per BFS follow-up node (up to 3) — so 1–4 times total. Each call covers one angle of the topic; the LLM decides what angles to explore based on what the previous call found. Max depth is 1 so the BFS is intentionally shallow but wide.
