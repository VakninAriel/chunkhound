HNSW metric extraction regex never matches — always rebuilds as cosine
chunkhound/providers/database/duckdb_provider.py:2080–2088 · _extract_hnsw_metric
🟠 High

_extract_hnsw_metric tries to recover the HNSW similarity metric by regex-matching metric='...' from the CREATE INDEX SQL stored in duckdb_indexes(). DuckDB silently strips the entire WITH (...) clause when persisting CREATE INDEX DDL to its catalog, so create_sql never contains metric=. The regex never matches and the function always returns "cosine".

Any HNSW index created with metric='l2' or metric='ip' is silently rebuilt as cosine after compaction. This corrupts search ranking without any error, warning, or indication that the metric changed. SpiGAndromeda confirmed this in their inline comment at line 2080, citing the external compactor which uses pragma_hnsw_index_info() instead. 

-- DuckDB catalog DDL (what the code actually receives):
CREATE INDEX idx_hnsw_1536 ON embeddings_1536 USING HNSW (embedding)
-- WITH (metric = 'l2') ← stripped by DuckDB catalog storage

-- What _extract_hnsw_metric regex looks for: metric='...'  → no match → "cosine"
Suggested fix
def _extract_hnsw_metric(self, conn: Any, index_name: str) -> str:
    """Recover HNSW metric from pragma_hnsw_index_info(), not catalog DDL."""
    try:
        row = conn.execute(
            "SELECT metric FROM pragma_hnsw_index_info(?) LIMIT 1",
            [index_name]
        ).fetchone()
        if row:
            return row[0]
    except Exception:
        pass
    return "cosine"  # safe fallback

Callers (_executor_get_vector_indexes_for_table at lines 2173 and 2243) must pass conn and the index name alongside create_sql.

_executor_reseed_sequence runs O(max_id) work on every compaction
chunkhound/providers/database/duckdb_provider.py:665–720 · _executor_reseed_sequence
also: _compact_finalize:1354, _executor_materialize_embedding_table:1712
🟠 High

duckdb_sequences().last_value is a binary flag (NULL = never used, 1 = used at least once), not the actual sequence counter. So after any sequence usage, current_value = 1 regardless of how many times nextval was called. This causes advance_by = max_id - 1 on every invocation, executing SELECT nextval(seq) FROM range(max_id - 1) — O(max_id) work.

Compaction path: _compact_finalize calls _executor_reseed_sequence for files and chunks (lines 1354). On a database with 2M files/chunks, compaction stalls for several seconds doing nothing useful. The comment at line 1360 acknowledges embeddings "can't use DROP" and uses the direct range(max_id) path — but _executor_recreate_sequence (which does use DROP + CREATE, O(1)) already exists and is used in _executor_rebuild_embedding_tables.

Normal operation path: _executor_materialize_embedding_table calls _executor_reseed_sequence for existing embedding tables (line 1712). Since this is called from _executor_ensure_embedding_table_exists on each embedding upsert batch, O(max_id) work runs per batch on any large database. 

# _executor_reseed_sequence — the bug
current_value_result = conn.execute(
    "SELECT last_value FROM duckdb_sequences() WHERE sequence_name = ?", [seq]
).fetchone()
current_value = current_value_result[0] if current_value_result else None
# last_value is BINARY FLAG (1 or NULL), not the actual counter!
# → advance_by = max_id - 1 every time
advance_by = max_id - int(current_value)
conn.execute(f"SELECT nextval('{seq}') FROM range({advance_by})")  # O(max_id)
Suggested fix
# Use _executor_recreate_sequence (O(1)) for all reseed paths:
def _executor_reseed_sequence(self, conn, table_name, sequence_name):
    max_result = conn.execute(
        f"SELECT COALESCE(MAX(id), 0) + 1 FROM {self._quote_duckdb_identifier(table_name)}"
    ).fetchone()
    next_value = int(max_result[0]) if max_result else 1
    self._executor_recreate_sequence(conn, sequence_name, next_value)

For embeddings in _compact_finalize, use _executor_recreate_sequence(conn, "embeddings_id_seq", max_embedding_id + 1) instead of the range(max_id) loop.

INSTALL vss in _compact_copy_data requires network — breaks offline compaction
chunkhound/providers/database/duckdb_provider.py:1208 · _compact_copy_data
🟡 Medium

The rebuild connection opens a fresh DuckDB database and immediately calls INSTALL vss. On an offline machine (air-gapped CI, disconnected dev environment, network failure during a long indexing run), this fails with a network error, causing auto-compaction to abort and the backup-then-swap state to trigger _compact_restore. The rollback path is correct, but the trigger is unnecessary — ChunkHound cannot run without vss already installed, so INSTALL vss → LOAD vss should be LOAD vss only. 

# Before (fails offline):
tgt_conn.execute("INSTALL vss")
tgt_conn.execute("LOAD vss")

# After:
tgt_conn.execute("LOAD vss")  # vss is always installed by the time we index

If forward compatibility with fresh installs is needed, guard with try: LOAD vss except: INSTALL vss; LOAD vss so the common path stays network-free.

preserve_insertion_order = false missing from rebuild connection — peak memory risk
chunkhound/providers/database/duckdb_provider.py:1206–1210 · _compact_copy_data
🟡 Medium

Three other bulk-write paths in this codebase set SET preserve_insertion_order = false before large INSERT ... SELECT operations (duckdb_provider.py:831, :2624, embedding_repository.py:494). This setting lets DuckDB use a memory-efficient streaming copy instead of buffering the full result in insertion order.

The _compact_copy_data rebuild connection (which copies all files, chunks, and every embedding table) doesn't set this flag. SpiGAndromeda's inline comment at line 1206 cites the external compactor's benchmarks: full rebuild peak RAM is 3–4× source table size on large indexes. For a 1.25 TB index, that was 11.8 GiB peak RSS just for HNSW rebuild. 

tgt_conn = duckdb.connect(str(compacted_path))
tgt_conn.execute("LOAD vss")
tgt_conn.execute("SET hnsw_enable_experimental_persistence = true")
tgt_conn.execute("SET preserve_insertion_order = false")  # ← add this
Crash-recovery warning silenced in MCP mode — significant event goes unlogged
chunkhound/providers/database/duckdb/connection_manager.py:596–600 · _recover_interrupted_compaction
🟡 Medium

When _recover_interrupted_compaction detects a .compact_backup file and a missing/empty live DB, it restores the database from the backup. This means a previous process died mid-compaction and the DB was atomically restored. It uses log_if_not_mcp("warning", "Recovering DuckDB database...") — which is completely suppressed under CHUNKHOUND_MCP_MODE=1 because loguru sinks are disabled in stdio mode.

Compare _compact_copy_data at lines 1290–1293, which explicitly prints the "dropped non-ChunkHound tables" warning to sys.stderr even in MCP mode, with the comment "Destructive operation — surface to stderr even in MCP mode." Crash recovery is at least as significant and should receive the same treatment. 

# Before (silent in MCP mode):
log_if_not_mcp("warning", "Recovering DuckDB database from interrupted compaction backup: ...")

# After (always surface):
msg = f"WARNING: Recovering DuckDB database from interrupted compaction backup: {backup_path}"
if os.environ.get("CHUNKHOUND_MCP_MODE") == "1":
    print(msg, file=sys.stderr)
else:
    logger.warning(msg)

_executor_embedding_table_needs_rebuild column default check is fragile
chunkhound/providers/database/duckdb_provider.py · _executor_embedding_table_needs_rebuild
🟢 Minor

_executor_embedding_table_needs_rebuild checks id_default != "nextval('embeddings_id_seq')" and dims_default != str(dims) as string comparisons against values returned by information_schema.columns.column_default. DuckDB may format these differently (e.g. nextval('embeddings_id_seq'::regclass) or with whitespace variation) across versions, causing false positives that trigger unnecessary full table rebuilds during compaction.

Consider using _executor_table_has_primary_key and a behavioral check (actually attempt to insert via the sequence and rollback) rather than string-matching DDL representations.

Overall Recommendation

The compaction architecture is well-designed — crash recovery, atomic swap, HNSW bookend protocol, and the MCP logging guard are all solid. The three-phase guard (set flag → close connections → rename file) correctly prevents reconnects from corrupting in-progress compaction state, and the pre-submit compaction check in the executor is the right location.

Two high-severity bugs need fixing before merge: (1) HNSW metric is always silently rebuilt as cosine post-compaction, corrupting non-cosine indexes; (2) the O(max_id) sequence reseed will cause multi-second stalls on large databases both during compaction and on normal embedding table access. The three medium issues (offline INSTALL vss, missing preserve_insertion_order, silent crash-recovery log) are straightforward one-liners each.
