Bottom Line

TurboVec is viable for ChunkHound's actual usage pattern (top-10 retrieval), once four corrections are folded into the design. The blocking engineering risk identified mid-POC — the private from_parts() API — now has two independently tested, working solutions. No forking or patching of turbovec was needed for either.

This POC (test-crates/turbovec-poc/, throwaway spike, no production code touched) validated every headline claim in the design doc against this repo's own real, indexed embeddings — not synthetic data. Four of the doc's claims needed correction, one deeper technical blocker was found and resolved, and the alarming-looking recall@1 number was run down to a specific, well-understood cause rather than left as an open question.

The from_parts() Problem — Two Options, Both Tested

The design doc's embeddings_quantized table has one stated purpose: rebuild the index from durable per-vector bytes if the main snapshot is lost, with no re-embedding. That's blocked by finding #2 above. We built and tested two independent solutions against this repo's real corpus — full detail in test-crates/turbovec-poc/README.md.

Option 1 — pin to the unreleased upstream fix

The exact fix (PR #204) is merged on turbovec's main branch, not yet released to crates.io. Git-pinned our dependency to that commit; a new test proves the design doc's original mechanism works end to end — bit-identical results, no snapshot blob, no re-embedding. One gap found: IdMapIndex itself still has no accessor for its inner index, so any real implementation has to hand-roll the id-reattachment layer regardless.

Trade-off: depends on an untagged, unreleased commit — safe today (content-addressed SHA pin), but not a versioned release we'd want to ship long-term without upstream cutting an actual tag.

Option 2(C) — durability engineering, no from_parts() needed

Works against the stable, published crate today. Checksummed, rotating snapshots plus keeping ChunkHound's existing float32 table as the true last resort.

Recommendation: ship this option as the safety net regardless of what else gets decided. It's cheap, uses only the stable published API, and every claim above is now proven by a passing test — not designed on paper. Revisit Option 1 once turbovec cuts an actual tagged release.

Why Recall@1 Looked Alarming (and What It Actually Means)

Recall@1 measured 0.89 at production scale — far below the claimed 0.997. Two mechanisms were tested, cheapest first, using this repo's own code corpus:

Near-tie ambiguity (the main driver)

Misses cluster almost entirely on queries where the true top-1 and top-2 chunks were already near-indistinguishable in exact, unquantized similarity (mean score gap 0.0009 on misses vs. 0.0589 on hits — a ~65x difference). This corpus has many near-duplicate chunks; any approximate method would struggle the same way. Not a TurboVec defect.

Embedding truncation (a smaller, real factor)

On a controlled matched sample, recall@1 improved from 0.9367 (256-dim, truncated) to 0.9700 at native 2560-dim — real dimensions matter, but the effect is modest and disappears entirely by k=3.

At k=10 — ChunkHound's actual default page size — recall is 1.0000 at every dimension and bit-width tested. The gap is real but confined to strict top-1 matching, which the product doesn't rely on unless something specific does (see "What Needs Your Decision" above).
